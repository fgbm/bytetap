# Запуск из командной строки

Страница временная: интерфейс появится в M2, а до тех пор обмен снимается консольной версией `bytetap-cli`. Она собирается из исходников там, где установлен Rust: `cargo build --release -p bytetap-cli` (готовый файл — `target\release\bytetap-cli.exe`). В архив релиза пока входит только `bytetap.exe` с интерфейсом.

## Запись обмена: `capture`

```powershell
bytetap-cli capture --listen 0.0.0.0:5000 --responder hl7
```

| Параметр | Смысл |
|----------|-------|
| `--listen ADDR` | Адрес и порт, на которых ждать анализатор. `0.0.0.0:5000` — все сетевые интерфейсы, `127.0.0.1:5000` — только этот компьютер (годится для проверки без анализатора) |
| `--responder hl7` | Автоответчик HL7/MLLP: на каждое сообщение анализатор получает ACK (FR-16) |
| `--responder none` | Без ответов: байты только пишутся в журнал. Для анализатора, которому подтверждения не нужны, или чтобы увидеть, что он присылает без ответа |
| `--log-dir DIR` | Папка журналов вместо `<домашняя папка>\Documents\bytetap` |
| `--analyzer TEXT` | Модель анализатора в заголовке журнала, например `"Analyzer X"` |
| `--note TEXT` | Комментарий инженера в заголовке журнала, например `"три пробы, режим ORU"` |

При старте программа печатает путь к файлу журнала и, если папка журналов лежит в OneDrive или на сетевом диске, предупреждение: журналы могут содержать данные пациентов и не должны уезжать в облако (FR-19).

Дальше идёт лента обмена. В каждой строке — время, стрелка направления, номер соединения и `text` фрагмента в том же виде, что в журнале: управляющие символы записаны как `<VT>`, `<FS>`, `<CR>` и так далее (FR-22).

```text
Журнал: C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl
Слушаю 0.0.0.0:5000 (Ctrl+C — остановка)
Лента:
10:15:03.000 ── #1 подключён 192.168.1.50:49152
10:15:03.001 → #1 <VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101500||ORU^R01|MSG0001|P|2.3.1<CR>PID|1||PATIENT^TEST<CR><FS><CR>
10:15:03.002 ← #1 [авто] <VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101530+0300||ACK^R01|BT261019101530000001|P|2.3.1<CR>MSA|AA|MSG0001<CR><FS><CR>
10:15:04.500 ── #1 закрыт: analyzer (eof)
```

- `→` — от анализатора к ЛИС, `←` — от ЛИС к анализатору.
- `[авто]` — байты сформировал автоответчик, а не прибор или ЛИС (FR-4).
- Длинный `text` обрезан для экрана; в журнале он записан целиком.
- Строки `──`, `!!` и `..` — открытие и закрытие соединения, ошибка и замечание обработчика.

Анализатор может переподключаться: каждое новое соединение получает следующий номер (`#2`, `#3`…), в журнале это отдельные события `open` и `close`.

Остановка — `Ctrl+C`; на Unix это ещё и `SIGTERM`/`SIGHUP` (служба, закрытая консоль), на Windows — кнопка закрытия и `Ctrl+Break`, то есть обычные способы остановить программу. SIGHUP, который процесс получил уже проигнорированным (`nohup`, служба), остановкой не считается: программу просили пережить закрытие терминала. Программа закрывает соединения, дописывает журнал и печатает итоги: сколько было соединений и сколько байтов прошло в каждую сторону. Последняя строка журнала — `session_end` с теми же числами (FR-22).

Если писатель журнала отказал (ошибка записи на диск), сессия останавливается сама: подтверждений анализатору больше не отправляется, а `capture` печатает «Запись в журнал прервана: <причина>. Сессия остановлена, анализатор не получил подтверждений после сбоя.» и выходит с кодом ≠ 0. Отказ замечается сразу, даже если анализатор молчит. Одна оговорка: ACK уходит раньше, чем пачка попадает на диск, поэтому сообщения из пачки, писавшейся в момент сбоя, могли получить подтверждение, но в журнал не попасть. Если журнал не удалось дописать за десять секунд, остановка сообщает «journal not flushed» и завершается: ждать зависшую запись бессмысленно. Если сессия не началась (занят порт, недоступна папка журналов), программа печатает «Не удалось начать сессию: …».

## Проверка журнала: `verify`

```powershell
bytetap-cli verify C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl
```

Проверка идёт по встроенной схеме формата и по правилам, которых схема не видит: `len` и `text` должны выводиться из `b64`, заголовок `session` — быть один и первым, после `session_end` допустим только `note`, суммы байтов не переполняются. В конце печатается статистика: число строк, событий по типам, байты по направлениям, число соединений. Код выхода ≠ 0 — журнал повреждён; обрезанная последняя строка (аварийное завершение) — только предупреждение.

## Комментарий после записи: `note`

```powershell
bytetap-cli note C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl "прогнали три пробы, анализатор Analyzer X"
```

Событие `note` дописывается в конец файла, начало журнала не переписывается (FR-23). Пока сессия пишет, дописать комментарий нельзя — команда отвечает «файл занят: идёт сессия или его держит другая программа», — а вот читать журнал на ходу можно: `verify` и Блокнот работают и во время записи.

## Вывод в файл в Windows PowerShell 5.1

При перенаправлении вывода `capture` в файл или в другую программу Windows PowerShell 5.1 кодирует его не в UTF-8, и кириллица превращается в знаки вопроса. Перед запуском задайте кодировку вывода:

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
bytetap-cli capture --listen 0.0.0.0:5000 --responder hl7 > capture.txt
```

## Брандмауэр

Первый запуск на прослушивании порта Windows показывает запрос брандмауэра. Анализатор подключается к ноутбуку, поэтому соединение входящее и без разрешения брандмауэр его не пропустит (NFR-4). Что отвечать и что делать без прав администратора — на странице [Брандмауэр](/guide/firewall).

## Персональные данные

Журнал содержит «сырой» обмен, а значит может содержать ФИО, даты рождения и идентификаторы пациентов. Файлы хранятся только на этом компьютере, но перед публикацией или передачей их нужно обезличить вручную: [Персональные данные](/guide/personal-data), FR-32 и FR-34.
