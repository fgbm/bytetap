# Запуск из командной строки

Страница временная: тот же обмен снимает графическая версия, а консольная `bytetap-cli` остаётся для машин без окна и для сценариев. Она собирается из исходников там, где установлен Rust: `cargo build --release -p bytetap-cli` (готовый файл — `target\release\bytetap-cli.exe`). В архив релиза пока входит только `bytetap.exe` с интерфейсом.

## Запись обмена: `capture`

```powershell
bytetap-cli capture --listen 0.0.0.0:5000 --responder hl7
bytetap-cli capture --connect 192.168.1.50:5000 --responder astm
bytetap-cli capture --serial COM5 --baud 9600 --format 8N1 --responder auto
bytetap-cli capture --proxy 0.0.0.0:50025 --to 10.0.0.5:5000 --role analyzer-client --allow-from 192.168.1.51
bytetap-cli capture --monitor COM3 --to COM4
bytetap-cli capture --monitor COM3 --to COM4 --baud 9600 --format 8N1 --to-baud 19200 --to-format 7E2
```

Источник соединений указывается ровно один: `--listen`, `--connect`, `--serial`, `--proxy` или `--monitor`. Два источника одновременно clap не пропустит.

| Параметр | Смысл |
|----------|-------|
| `--listen ADDR` | Ждать анализатор на адресе. `0.0.0.0:5000` — все сетевые интерфейсы, `127.0.0.1:5000` — только этот компьютер |
| `--connect HOST:PORT` | Подключиться к анализатору-серверу. Анализатор может быть выключен при старте: первая неудачная попытка станет ошибкой в журнале, дальше программа повторит подключение |
| `--reconnect-sec N` | Интервал переподключения, 0…3600 секунд, по умолчанию 5. Работает с `--connect` (к анализатору) и с `--monitor` (открытие обоих портов после разрыва) |
| `--serial NAME` | Открыть COM-порт вместо ЛИС: `COM5` на Windows, `/dev/ttyUSB0` на Linux |
| `--proxy ADDR` | Встать в разрыв: слушать этот адрес и на каждое входящее соединение подключаться к цели. `--to` и `--role` обязательны |
| `--to HOST:PORT \| NAME` | Вторая сторона пары. У прокси — адрес цели: ЛИС в топологии «анализатор — клиент» или анализатора в «анализатор — сервер». У прослушки — имя порта ЛИС: `COM4`, `/dev/ttyUSB1`. Обязателен с `--proxy` и с `--monitor` |
| `--monitor NAME` | Прослушка двух COM-портов: встать в разрыв кабеля, `NAME` — порт стороны анализатора (`COM3`, `/dev/ttyUSB0`), `--to` — порт стороны ЛИС. Байты идут в обе стороны без изменений, автоответчика нет (FR-10) |
| `--to-baud N`, `--to-format FORMAT` | Скорость и формат порта ЛИС; без флагов — те же, что у порта анализатора |
| `--to-flow FLOW`, `--to-dtr on\|off`, `--to-rts on\|off` | Поток и линии порта ЛИС; без флагов — те же, что у порта анализатора |
| `--role analyzer-client\|analyzer-server` | Кто подключается к bytetap: `analyzer-client` — анализатор приходит сам, bytetap идёт к ЛИС; `analyzer-server` — приходит ЛИС, bytetap идёт к анализатору. Только с `--proxy` |
| `--allow-from IP` | Принимать входящие только с этого адреса (IPv4 или IPv6, без порта). Входящее с другого адреса закрывается сразу, не подключаясь к цели. Без флага принимается любой адрес сети. Адрес другого семейства, чем `--proxy`, — ошибка аргументов: такое входящее не совпадёт ни с кем; `[::]` держит двойной стек и принимает оба семейства, а `::ffff:a.b.c.d` — тот же IPv4. Только с `--proxy` |
| `--baud N` | Скорость порта 1…4 000 000; типовые 300–115200. Обязательна с `--serial`, у `--monitor` относится к порту анализатора (по умолчанию 9600) |
| `--format FORMAT` | `<биты><чётность><стоп>`: `8N1`, `7E2`, `8M1`, `7O1`. Чётность: `N` — нет, `E` — чётная, `O` — нечётная, `M` — mark, `S` — space. Обязательна с `--serial`, у `--monitor` — по умолчанию `8N1` |
| `--flow none\|rtscts\|xonxoff` | Управление потоком; по умолчанию `none` |
| `--dtr on\|off`, `--rts on\|off` | Начальное состояние линий; по умолчанию обе `on` |
| `--responder auto\|hl7\|astm\|none` | Автоответчик: `auto` — определить протокол по первому байту, `hl7` — HL7/MLLP, `astm` — ASTM E1381, `none` — без ответов. Параметр обязателен, чтобы журнал не зависел от умолчания версии. С `--proxy` и `--monitor` несовместим: там автоответчика нет, байты идут без изменений (FR-6, FR-10) |
| `--astm-nak` | ASTM: отвечать `NAK` на неверную контрольную сумму вместо `ACK`. С `--proxy` и `--monitor` несовместим |
| `--log-dir DIR` | Папка журналов вместо `<домашняя папка>\Documents\bytetap` |
| `--analyzer TEXT` | Модель анализатора в заголовке журнала, например `"Analyzer X"` |
| `--note TEXT` | Комментарий инженера в заголовке журнала, например `"три пробы, режим ORU"` |

При старте программа печатает, что делает: `Слушаю 0.0.0.0:5000`, `Подключаюсь к …`, `Порт COM5`, `Слушаю 0.0.0.0:50025 → 10.0.0.5:5000 (анализатор — клиент), только с 192.168.1.51` с фильтром по адресу или `Прослушка: COM3 ⇄ COM4 (9600 8N1, поток none)`, и путь к журналу. Если папка журналов лежит в OneDrive или на сетевом диске, печатается предупреждение: журналы могут содержать данные пациентов и не должны уезжать в облако. Если порт не найден или занят, журнал не создаётся, а программа печатает «Не удалось начать сессию: …».

COM-порт и TCP-клиент пишут журнал так же, как TCP-сервер: те же события `open`, `data`, `close`, `error`, `info`, тот же автоответчик. У COM-порта в событии `open` поле `peer` — имя порта, а `local` пустое: адресов у порта нет.

Прокси пишет тот же журнал своим режимом: `mode: proxy`, имя файла `bytetap-<дата>-<время>-proxy.jsonl`, `autoresponder: none`. Пара соединений — одно соединение журнала: `open` несёт обе стороны (`peer`/`local` принятой и `link` исходящей), `data` — направление по роли стороны, `close` — один на пару с тем, кто закрыл. Недоступная цель не создаёт соединения: в журнал идёт `error` с кодом `proxy_connect_failed` или `proxy_connect_timeout`, а сессия продолжает слушать.

Коды ошибок прокси — каждый называет свою причину, а не общее «не получилось»:

| Код | Когда |
|-----|-------|
| `proxy_connect_failed` | bytetap не подключился к цели: отказ в соединении, нет маршрута. Входящее закрыто, `open` не писался |
| `proxy_connect_timeout` | Цель не ответила за срок подключения (10 с) |
| `proxy_target_is_self` | Цель оказалась адресом прослушивания bytetap: пара не создаётся. Цель-адрес с тем же портом отвергается ещё на старте, имя узла ловится после подключения |
| `proxy_peer_rejected` | Входящее пришло с адреса, которого нет в `--allow-from`: закрыто до подключения к цели. Отказы схлопываются в одну серию и на разные адреса: `error` о первом, а сколько их было — в `repeats` замечания о серии |
| `accept_failed` | Сломался приём на порту прослушивания; повтор с растущей паузой |

Все они схлопываются, как ошибки источника в других режимах: одно `error` на серию, `info` с числом повторов и о восстановлении.

Прослушка двух портов пишет свой режим: `mode: com_monitor`, имя файла `bytetap-<дата>-<время>-com_monitor.jsonl`, `autoresponder: none`, `settings` — два блока фактических настроек (`analyzer` и `lis`). Пара открытых портов — одно соединение журнала: `open` несёт порт анализатора в `peer` и порт ЛИС в `link` с `role: "lis"`, `local` у обоих пустой (у порта нет адресов), `data` — направление по порту, `close` — один на пару. Пропажа адаптера одной стороны закрывает пару (`error` с кодом `connection_read_failed` или `connection_write_failed`, `close` с `by` этой стороны и `reason: "error"`), после чего оба порта переоткрываются: серия повторов схлопывается, новое `open` получает следующий `conn`.

Порты занимает только bytetap: закройте ЛИС и программу анализатора. Windows не открывает занятый COM-порт, на Unix `TIOCEXCL` не даёт открыть его второй раз, а в разрыве линии чужого обмена на том же порту всё равно нет.

Линии управления насквозь не передаются: DTR и RTS выставляются по настройке (по умолчанию подняты), CTS/DSR/DCD каждой стороны — линии самого bytetap. Аппаратный RTS/CTS в разрыве не работает, а `xonxoff` хуже: драйвер съедает `0x11` и `0x13` из обмена, и эти байты не попадают ни в ленту, ни в журнал. При выборе потока, отличного от `none`, программа печатает предупреждение — в разрыве поток обычно выключают.

Ошибки подключения и открытия порта схлопываются: в журнал попадает одно `error`, затем `info` о повторах и о восстановлении. Недоступный анализатор не забивает журнал строкой каждую секунду, а «Стоп» не ждёт паузу между попытками.

## Список портов: `ports`

```powershell
bytetap-cli ports
```

Команда печатает доступные COM-порты с понятным описанием: для USB-адаптера — продукт и производитель из VID/PID, например `USB-SERIAL CH340 (COM5)`, иначе имя порта. Сортировка по номеру: `COM2` раньше `COM10`. Пустой список — не ошибка: на машине без портов команда так и говорит.

Дальше идёт лента обмена. В каждой строке — время, стрелка направления, номер соединения и `text` фрагмента в том же виде, что в журнале: управляющие символы записаны как `<VT>`, `<FS>`, `<CR>` и так далее.

```text
Журнал: C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl
Слушаю 0.0.0.0:5000 (Ctrl+C — остановка)
Лента:
10:15:03.000 ── #1 подключён 192.168.1.50:49152
10:15:03.001 → #1 <VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101500||ORU^R01|MSG0001|P|2.3.1<CR>PID|1||PATIENT^TEST<CR><FS><CR>
10:15:03.002 ← #1 [авто] <VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101530+0300||ACK^R01|BT261019101530000001|P|2.3.1<CR>MSA|AA|MSG0001<CR><FS><CR>
10:15:04.500 ── #1 закрыт: analyzer (eof)
```

- `→` — от анализатора к ЛИС, `←` — от ЛИС к анализатору.
- `[авто]` — байты сформировал автоответчик, а не прибор или ЛИС.
- Длинный `text` обрезан для экрана; в журнале он записан целиком.
- Строки `──`, `!!` и `..` — открытие и закрытие соединения, ошибка и замечание обработчика.

Анализатор может переподключаться: каждое новое соединение получает следующий номер (`#2`, `#3`…), в журнале это отдельные события `open` и `close`.

Остановка — `Ctrl+C`; на Unix это ещё и `SIGTERM`/`SIGHUP` (служба, закрытая консоль), на Windows — кнопка закрытия и `Ctrl+Break`, то есть обычные способы остановить программу. SIGHUP, который процесс получил уже проигнорированным (`nohup`, служба), остановкой не считается: программу просили пережить закрытие терминала. Программа закрывает соединения, дописывает журнал и печатает итоги: сколько было соединений и сколько байтов прошло в каждую сторону. Последняя строка журнала — `session_end` с теми же числами.

Если писатель журнала отказал (ошибка записи на диск), сессия останавливается сама: подтверждений анализатору больше не отправляется, а `capture` печатает «Запись в журнал прервана: <причина>. Сессия остановлена, анализатор не получил подтверждений после сбоя.» и выходит с кодом ≠ 0. Отказ замечается сразу, даже если анализатор молчит. Одна оговорка: ACK уходит раньше, чем пачка попадает на диск, поэтому сообщения из пачки, писавшейся в момент сбоя, могли получить подтверждение, но в журнал не попасть. Если журнал не удалось дописать за десять секунд, остановка сообщает «journal not flushed» и завершается: ждать зависшую запись бессмысленно. Если сессия не началась (занят порт, недоступна папка журналов, порт не найден), программа печатает «Не удалось начать сессию: …».

Имя файла зависит от режима: `…-tcp_server.jsonl`, `…-tcp_client.jsonl`, `…-proxy.jsonl`, `…-serial.jsonl` или `…-com_monitor.jsonl`.

## Проверка журнала: `verify`

```powershell
bytetap-cli verify C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl
```

Проверка идёт по встроенной схеме формата и по правилам, которых схема не видит: `len` и `text` должны выводиться из `b64`, заголовок `session` — быть один и первым, после `session_end` допустим только `note`, суммы байтов не переполняются. В конце печатается статистика: число строк, событий по типам, байты по направлениям, число соединений. Код выхода ≠ 0 — журнал повреждён; обрезанная последняя строка (аварийное завершение) — только предупреждение.

## Комментарий после записи: `note`

```powershell
bytetap-cli note C:\Users\user\Documents\bytetap\bytetap-20261019-101500-tcp_server.jsonl "прогнали три пробы, анализатор Analyzer X"
```

Событие `note` дописывается в конец файла, начало журнала не переписывается. Пока сессия пишет, дописать комментарий нельзя — команда отвечает «файл занят: идёт сессия или его держит другая программа», — а вот читать журнал на ходу можно: `verify` и Блокнот работают и во время записи.

## Вывод в файл в Windows PowerShell 5.1

При перенаправлении вывода `capture` в файл или в другую программу Windows PowerShell 5.1 кодирует его не в UTF-8, и кириллица превращается в знаки вопроса. Перед запуском задайте кодировку вывода:

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
bytetap-cli capture --listen 0.0.0.0:5000 --responder hl7 > capture.txt
```

## Брандмауэр

Первый запуск на прослушивании порта Windows показывает запрос брандмауэра. Анализатор подключается к ноутбуку, поэтому соединение входящее и без разрешения брандмауэр его не пропустит. Что отвечать и что делать без прав администратора — на странице [Брандмауэр](/guide/firewall).

## Персональные данные

Журнал содержит «сырой» обмен, а значит может содержать ФИО, даты рождения и идентификаторы пациентов. Файлы хранятся только на этом компьютере, но перед публикацией или передачей их нужно обезличить вручную: [Персональные данные](/guide/personal-data).
