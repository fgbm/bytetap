# Архитектура

Страница описывает устройство bytetap v0.2.0 по фактическому коду: из чего собран продукт, как байты проходят от анализатора до журнала и ленты, как начинается и заканчивается сессия, как читается сохранённый журнал и что мешает приложению выйти в сеть. Критерии приёмки этапов — в [M1](/dev/stages/M1), [M2](/dev/stages/M2), [M3](/dev/stages/M3) и [U1](/dev/stages/U1); решения, которые стоят за устройством, — в [ADR](/dev/adr/).

С v0.2.0 оболочка нативная: `crates/bytetap-app` на egui, eframe и wgpu вместо Tauri и Vue ([ADR 0003](/dev/adr/0003-native-ui)). Ядро, формат журнала, автоответчик и CLI от смены оболочки не изменились. Оболочка v0.1.0 (`app/`: Tauri и Vue) из репозитория удалена (U1-AC30), поэтому всё описание ниже — про нативное приложение; о мосте Tauri помнят только [этапы M2 и M3](/dev/stages/M2) и `CHANGELOG.md`.

## Компоненты

bytetap — один переносимый `bytetap.exe` и четыре крейта в `crates/`: ядро, CLI, приложение и тестовый набор. Ядро не зависит от оболочки: его можно собрать и проверить без окна.

| Компонент | Где | Что делает |
|-----------|-----|------------|
| Ядро `bytetap-core` | `crates/bytetap-core` | Сессия записи, источник соединений и транспорт `AsyncRead + AsyncWrite`, журнал `bytetap-session/1`, автоответчики HL7/MLLP, ASTM E1381 и «Авто». Не зависит ни от оболочки, ни от интерфейса. |
| CLI `bytetap-cli` | `crates/bytetap-cli` | `capture` (`--listen`, `--connect`, `--serial`), `ports`, `verify`, `note`. Работает на том же ядре, что и окно; схема журнала вшита в бинарь. |
| Приложение `bytetap-app` (v0.2.0) | `crates/bytetap-app` | Нативное окно без рамки и шапка, экраны сценариев, формы, запись, лента, трасса, просмотр журнала, настройки и профили, темы (`build.rs` и `design/tokens.css`), i18n, журнал запуска. Ядро вызывает напрямую, события берёт подпиской `broadcast` в кольцевой буфер на 10 000 событий; ввод-вывод уводит в фоновые задачи. |
| Общий разбор `‹CR›` | `shared/control-chips.ts` | Делит текст фрагмента на обычные куски и управляющие символы для примера обмена на сайте; в нативном приложении то же делает `feed.rs`. |
| Тестовый набор | `crates/bytetap-testkit` | Эмуляторы анализатора HL7/MLLP и ASTM E1381, тестовый TCP-сервер, пути к синтетическим фикстурам. Только для тестов, не публикуется. |
| Дизайн-токены | `design/tokens.css` | Единственный источник значений для приложения и сайта: цвета, кегли, отступы, радиусы, длительности. |
| Сайт | `docs` | VitePress: руководство, справочник, раздел разработки и примеры обмена. |

Направление зависимостей: `bytetap-cli` и `bytetap-app` зависят только от `bytetap-core`, а `bytetap-testkit` используется тестами крейтов. Обратных зависимостей нет: ядро ничего не знает ни про окно, ни про интерфейс.

## Поток данных

```
источник соединений                 serve (одна задача на соединение)
TcpServer | TcpClient | Serial
      │  Next::Connected(Connection { transport, peer, local })
      ▼
 run (сессия): нумерация conn, схлопывание ошибок, note
      │
      ├──► read 16 КиБ ──► Event::Data (dir a2l, mono_us)
      │        │
      │        ├──► ResponderKind::build ──► Auto | Hl7Mllp | Astm | None
      │        │        feed(&[u8], now) ──► Action::Send / Action::Event
      │        ├──► запись ответа в сокет ──► Event::Data (dir l2a, synthetic)
      │        └──► close / error / info
      ▼
 Shared::publish
      ├──► Journal::record ──► неограниченный mpsc ──► задача-писатель
      │        пачка ≤ 256 КиБ: write_all → flush → sync_data
      └──► broadcast<Arc<Event>> (1024 события, отставший получает Lagged)
               ▼
         live::pump — кольцевой буфер 10 000, request_repaint не чаще ~30 раз в секунду
               ▼
   recording::RecordingView ──► кольцевой буфер 10 000
               ├──► лента: виртуализация, текст или HEX
               └──► трасса: окно ~60 с при записи, плотность сессии при просмотре
```

Порядок событий одного соединения в журнале — порядок вызовов: `open` пишется до первых фрагментов этого соединения, затем входящий `data`, затем `data` синтетического ответа. Журнал не блокирует пересылку: `Journal::record` только кладёт событие в канал, а ответ уходит в сокет до записи в журнал.

Ключевые константы потока:

| Константа | Значение | Где |
|-----------|----------|-----|
| Буфер чтения | 16 КиБ на один вызов чтения — один фрагмент журнала | `session::READ_BUFFER` |
| Срок записи ответа | 5 с, затем `close` с причиной `timeout` | `session::WRITE_TIMEOUT` |
| Ожидание соединений при остановке | 2 с, затем задачи прерываются и `close` пишется за них | `session::CONNECTIONS_SHUTDOWN_TIMEOUT` |
| Ожидание писателя при остановке | 10 с, затем ошибка «journal not flushed» | `session::JOURNAL_SHUTDOWN_TIMEOUT` |
| Канал подписчиков | 1024 события; отставший теряет старые и получает `Lagged` | `session::EVENT_BUFFER` |
| Кольцевой буфер интерфейса | 10 000 событий; лишние отбрасываются со счётчиком «пропущено в ленте» | `feed::FEED_CAPACITY` |
| Страница журнала | 500 событий, не больше 1000 за команду | `journal.rs`, `journal::MAX_PAGE` |

## Жизненный цикл сессии

Старт идёт в одном порядке и до первого события:

1. Определяется папка журналов и предупреждение о OneDrive или сетевом пути (FR-19).
2. Открывается источник: занимается адрес или порт. Отказ источника — ошибка старта до создания файла, пустой журнал не остаётся.
3. Создаётся файл журнала, заголовок `session` пишется и фиксируется синхронно (FR-21). Имя занято — суффикс `-2`…`-99`.
4. Запускается задача сессии; `SessionHandle` отдаёт путь к журналу, фактический адрес, подписку на ленту и счётчики.

Соединения обслуживаются задачами `serve`; TCP-сервер принимает несколько параллельно, TCP-клиент и COM-порт — по одному (`ConnectionSource::sequential`). Ошибки `accept`, подключения и открытия порта схлопываются: одно `error`, затем `info` о повторах и о восстановлении. Недоступный анализатор не забивает журнал строкой в секунду, а «Стоп» не ждёт паузу между попытками.

Остановка штатная:

- сигнал `stop` закрывает слушатель и задачи соединений; каждое соединение получает `close` с причиной `stop`, если не успело закрыться само;
- очередь комментариев дочитывается до `session_end` (FR-23);
- в журнал пишется `session_end` со счётчиками, писатель дописывает накопленное и фиксирует файл;
- `SessionHandle::stop` возвращает статистику. Выгрузка дескриптора без `stop` посылает только сигнал и штатной остановкой не считается.

Сессия в окне. В нативном приложении окно одно, поэтому слот сессии живёт в `app.rs`, а не в мосте: поколений и повторной подписки после перезагрузки страницы нет, потому что перезагружать нечего.

Отказ журнала. Первый `false` от `Journal::record` означает, что события больше не попадают на диск:

- подписчикам уходит `error` с кодом `journal_failure` и причиной, интерфейс показывает строку под шапкой с двумя действиями;
- ответов анализатору больше нет: ни одного ACK после отказа, чтобы прибор не считал обмен успешным, которого нет в журнале;
- соединения закрываются, `session_end` не пишется, `SessionHandle::stop` возвращает ошибку с причиной, а `bytetap-cli capture` печатает «Запись в журнал прервана» и выходит с кодом ≠ 0.

Закрытие окна и выход. Запрос закрытия при идущей записи отменяется: `app.rs` останавливает сессию и только потом закрывает окно; если остановка не уложилась в `live::STOP_WAIT` (15 с), приложение всё равно выходит, а предупреждение о неполном журнале — системное сообщение после выхода из окна (U1-AC17, NFR-5).

## Журнал

Запись. Писатель — отдельная задача `tokio` за неограниченным каналом `mpsc` (ADR [0001](/dev/adr/0001-journal-writer)):

- `record` никогда не ждёт диск; медленный диск не задерживает пересылку (NFR-6);
- задача забирает всё накопленное (`recv` + `try_recv`), пишет строки одним `write_all`, делает один `flush` и один `sync_data` на пачку (FR-20);
- пачка ограничена `MAX_BATCH_BYTES` (256 КиБ), остаток канала уходит следующей пачкой без переупорядочивания;
- очередь ограничена по объёму — `MAX_PENDING_BYTES` (64 МиБ): на половине предела сессия пишет одно `info` с кодом `journal_backlog_warning`, на пределе `record` отказывает кодом `journal_backlog`, и сессия останавливается как при сломанном диске. Иначе неограниченный канал при медленном диске съел бы память целиком;
- файл защищён от второй записи: на Unix — рекомендательная `flock`, на Windows — режим совместного использования без права записи; читать журнал при этом можно;
- `note` дописывается в конец в режиме `O_APPEND`, начало файла не переписывается, обрезанный хвост не дописывается;
- после аварийного завершения теряется только последняя неполная строка: записанные пачки уже прошли `sync_data`.

Формат, поля и правила экранирования `text` — в [справочнике формата журнала](/reference/session-format), JSON Schema — `docs/public/schema/bytetap-session-2.schema.json` (журналы `/1` проверяются схемой `bytetap-session-1.schema.json`). Тексты `error` и `info` в журнале английские, русский язык живёт в интерфейсе; код события (`code`) интерфейс переводит сам.

Чтение. Интерфейс не загружает журнал целиком (FR-29):

- первый проход строит индекс: смещения строк событий ленты, длину каждого события (`lens`), монотонное время, гистограмму плотности на 600 корзин и таблицу `firstEvent` на 601 точку «первое событие корзины»;
- индекс кешируется по пути в LRU на 8 журналов; сборка одного пути идёт под отдельным замком, чтобы два окна не индексировали файл параллельно;
- выросший файл доиндексируется с последнего целого смещения: перед этим проверяется, что начало файла и перевод строки на прежнем конце те же, иначе индекс собирается заново — иначе смещения указывали бы в чужой журнал;
- `read_journal(path, from, count)` читает страницу по смещениям, а `journal_lengths` отдаёт длины событий, чтобы лента знала высоты HEX-строк, не читая файл;
- таблица `firstEvent` переводит долю времени на трассе в номер события и обратно, поэтому рамка видимой области и переход по щелчку считаются по времени, а не по пропорции номеров строк.

Индекс, кеш и постраничное чтение живут в ядре — `bytetap_core::journal::view` (`JournalCache::index`/`open`/`read`, `JournalIndex`, `append_note`), без зависимости от оболочки: вызовы блокирующие, оболочка сама уводит их с потока окна. Строка длиннее `MAX_LINE_BYTES` (64 МиБ) считается битой; хеш начала файла (до 4 КБ) при доиндексации сверяется на той же длине, что и при сборке, поэтому короткий журнал после дописанного комментария тоже доиндексируется, а не собирается заново.

Битая строка не ломает просмотр: она пропускается, `verify` считает её отдельно. Обрезанная последняя строка — предупреждение, а не ошибка (T-4).

## Автоответчик и транспорт

Автоответчик — sans-IO автомат (`responder`): он не знает ни про сокеты, ни про журнал, получает фрагмент и время снаружи и возвращает `Action::Send` или `Action::Event`. Поэтому поведение одинаково для TCP и COM, а тесты детерминированы. Время `now` передаёт сессия, она же держит срок `poll_timeout`: по нему ASTM сообщает о недособранном кадре, не дожидаясь следующего соединения.

`ResponderKind` собирает автомат на соединение: `Hl7` (MLLP), `Astm { nak_on_bad_checksum }`, `Auto` и `None`. «Авто» принимает решение один раз по первому значимому байту соединения: `0x0B` — HL7/MLLP, `0x05` — ASTM E1381, иначе запись идёт без ответов с предупреждением `protocol_undetected`. Номера `MSH-10` берутся из общего на сессию `ControlIdSource`, поэтому не повторяются между соединениями. Подробности профилей — в [справочнике автоответчика](/reference/autoresponder).

Транспорт — `AsyncRead + AsyncWrite`: `serve` не различает сокет и COM-порт. Источник (`ConnectionSource`) отдаёт `Next::Connected(Connection)` либо `Next::Retry { error, after, stage }`; сессия решает, когда писать `error`, и ждёт паузу в `select!` вместе с остановкой и отказом журнала. `stage` (приём, подключение, открытие порта) задаёт код ошибки: один и тот же отказ подключения у TCP-клиента и цели прокси называется по-разному, а сломанный `accept` не путается с недоступной целью. Источников четыре: `TcpServer`, `TcpClient` с переподключением, `Serial` и `Proxy`; прослушка COM станет пятым, а не второй копией сессии.

## Прокси между анализатором и ЛИС

Прокси — не вторая сессия, а четвёртый источник (FR-5…FR-8, M4-AC16). `Source::Proxy { listen, target, role, retry }` занимает порт прослушивания и больше ничего: недоступная цель стартом не проверяется, её отказ станет событием `error`, а не отказом запуска. Стартом отвергается только петля на себя: цель, совпавшая с адресом прослушивания (с учётом `0.0.0.0` и петлевых адресов), — ошибка `proxy_target_is_self`, иначе bytetap подключился бы к своему же порту.

Подключение к цели идёт задачей в `JoinSet` внутри `ProxySource`, а не в самом будущем `next`. Сессия вызывает `source.next()` в `select!` вместе с остановкой, отказом журнала, комментарием и закрытием соседней пары, поэтому `next` отменяется в произвольный момент. Принятый сокет и начатое подключение переезжают в задачу целиком, и отмена их не теряет: результат заберёт следующий вызов. Отсюда же параллельность: пара, ждущая молчащую цель, не задерживает следующую. `next` — `select!` из приёма и `join_next`: приём запускает задачу подключения, `join_next` отдаёт готовую пару или `Next::Retry`. Пара, у которой `link.local` совпал с `peer` принятого сокета (оба конца — одно соединение), отбрасывается до `open`.

`Next::Retry` несёт ещё и этап (`Stage`: приём, подключение, открытие порта): от этапа зависит код в журнале, и у прокси сломанный `accept` — это `accept_failed`, а не недоступная цель.

Топология — настройка, а не догадка: `role: analyzer_client` (bytetap слушает для анализатора и идёт к ЛИС) или `analyzer_server` (слушает для ЛИС и идёт к анализатору). `Connection::link` — исходящая сторона пары: транспорт, роль дальнего конца (`analyzer` или `lis`) и его адреса. По роли считается направление: байты из сокета анализатора всегда `analyzer_to_lis`, из сокета ЛИС — `lis_to_analyzer`, кто бы ни начал соединение.

`serve_proxy` держит пару двумя насосами, по одному на направление: каждый читает в свой буфер `READ_BUFFER` (16 КиБ), собирает событие `data` по времени чтения, пишет прочитанное в другой сокет и только потом кладёт событие в журнал — с фактически переданными байтами, поэтому в записи ровно то, что получил адресат. Время `mono_us` относится к чтению: строки двух направлений могут встать в файле не по времени, но время в них причинное (см. `reference/session-format.md`). Запись в сокет идёт в `select!` с остановкой, отказом журнала и сигналом пары, поэтому адресат, переставший читать, не держит пару, а отмена записи не теряет отправленный кусок. `TCP_NODELAY` включён на обоих сокетах, а на пути данных нет искусственных сроков: медленный адресат притормаживает обратное направление окном TCP, а не рвётся по таймауту, иначе bytetap сам вызвал бы таймаут протокола у анализатора. Журнал в пересылку не входит; его отказ останавливает пересылку, чтобы ЛИС не получила обмен, которого нет в записи.

Закрытие по FR-7 — одно `close` на пару: `FIN` одной стороны пересылается полузакрытием (`shutdown` записи в другую), обратное направление доживает до своего `FIN`, но не дольше `PROXY_LINGER` (5 с), после чего пара закрывается как `bytetap/timeout`; `RST` закрывает обе стороны сразу; «Стоп» — `by: bytetap`, `reason: stop`. Второй насос останавливается сигналом, а не `abort`: прерванная посреди записи задача не успела бы записать в журнал отправленные байты. Ошибка второго направления во время дожития (сброс) пишется в журнал событием `error` с номером пары, но `close` остаётся за стороной, закрывшей первой. При `reason: reset` обе стороны закрываются с `SO_LINGER 0`: собеседник получает сброс, а не `FIN`, и не ждёт закрытия полуоткрытого соединения. Автоответчика в прокси нет вообще (FR-6): `SessionConfig::proxy` подставляет профиль `none`, а `with_responder` на прокси не действует.

COM-порт устроен по [ADR 0002](/dev/adr/0002-serial-port): крейт `serialport` с блокирующим чтением в отдельном потоке (таймаут 50 мс), запись — во втором потоке через очередь команд с `oneshot`-ответом, mark/space выставляются прямыми вызовами платформенных API, остановка не соединяет потоки и не ждёт зависшую в драйвере запись.

## Безопасность и персональные данные

- FR-33: приложение ничего не отправляет по сети, кроме трафика самой сессии. Нет телеметрии, автообновлений, загрузки журналов и внешних запросов. В v0.2.0 в процессе нет вебвью: интерфейс — Rust-код, и послаблений CSP, плагинов и областей файловой системы просто нет.
- Пути выбираются системным диалогом (`rfd`), а не приходят из интерфейса: в v0.2.0 окно — тот же процесс, но файловую систему трогает только код, который открывает журнал или папку по выбранному пути.
- Журналы хранятся только локально и не обезличиваются (FR-32): перед публикацией или передачей их нужно обезличить вручную. Тестовые журналы в репозитории синтетические.

## Тестирование

Уровни проверок и ручные сценарии подробно описаны в [тестировании](/dev/testing); здесь — соответствие коду.

| Уровень | Что проверяет | Где |
|---------|---------------|-----|
| Unit, ядро | Экранирование `text` для всех байтов, писатель и групповая фиксация, читатель и обрезанная строка, автоматы MLLP, ASTM и «Авто», в том числе proptest на любую нарезку потока | `crates/bytetap-core/src/**`, `#[cfg(test)]` рядом с кодом |
| Интеграционные, loopback | Эмулятор анализатора из `bytetap-testkit` ↔ сессия: склейка `b64` равна отправленному, ACK на каждое сообщение, переподключения, отказ журнала, остановка | `crates/bytetap-core/tests/*.rs` |
| Процесс CLI | `capture` под нагрузкой, штатная остановка, `verify` и `note`, устойчивость к SIGKILL | `crates/bytetap-cli/tests/*.rs` |
| COM на pty | Пара `socat`, ASTM через порт, отсутствие лишних `info`/`error`; тест `#[ignore]`, в CI запускается отдельно с `BYTETAP_REQUIRE_SOCAT=1` | `crates/bytetap-core/tests/serial.rs` |
| Приложение без окна (v0.2.0) | Настройки и профили, кольцо ленты и HEX, кодировки, i18n-ключи, валидация, индекс журнала, перевод доли времени в событие | `crates/bytetap-app/src/**`, `#[cfg(test)]` |
| Экраны (v0.2.0) | Снимки `egui_kittest` всех экранов в обеих темах, DPI 125 и 150 %, дерево AccessKit и порядок Tab, кадры в простое и при записи | `crates/bytetap-app/tests/*.rs` |
| Сайт | Битые внутренние ссылки навигации | `scripts/check-docs-links.mjs` |

Один прогон перед сдачей — `npm run check` из корня: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --no-fail-fast` и проверка ссылок. Отдельно собирается сайт (`npm run docs:build`): npm в репозитории обслуживает только документацию.

## Где что лежит

```
bytetap/
├── crates/
│   ├── bytetap-core/          ядро без оболочки
│   │   ├── src/journal/       события, писатель, читатель
│   │   ├── src/responder/     hl7, mllp, astm, auto
│   │   ├── src/transport/     tcp, serial
│   │   ├── src/session.rs     актор сессии, соединения, счётчики
│   │   ├── src/text.rs        экранирование управляющих байтов
│   │   └── tests/             loopback, отказ журнала, pty
│   ├── bytetap-cli/           capture, ports, verify, note
│   ├── bytetap-app/           нативное окно v0.2.0: app, screens, live, feed, journal,
│   │                          viewing, settings, theme (build.rs из tokens.css), locales/
│   └── bytetap-testkit/       эмуляторы анализатора и фикстуры
├── shared/control-chips.ts    разбор управляющих символов для примера обмена на сайте
├── design/                    tokens.css, tokens-system.css
├── docs/                      VitePress: guide, reference, dev, public
└── tests/fixtures/            синтетические журналы, HL7 и ASTM
```
