# Тестирование

Документ для участников проекта и владельца: что проверяется автоматически в CI, что проверяется руками на Windows-сборке и как это сделать.

## Автоматические проверки

Один прогон перед сдачей — из корня репозитория:

```bash
npm run check
```

Скрипт последовательно запускает:

- `cargo fmt --all --check` — форматирование;
- `cargo clippy --workspace --all-targets -- -D warnings` — предупреждения как ошибки;
- `cargo test --workspace --no-fail-fast` — тесты ядра, CLI и приложения, включая интеграционные на loopback и тесты прослушки двух портов на виртуальной паре (COM-тесты на pty помечены `#[ignore]` и запускаются отдельно, см. ниже);
- `node scripts/check-docs-links.mjs` — ссылки навигации сайта.

Отдельно собирается сайт документации:

```bash
npm run docs:build
```

Windows-сборка exe (то же, что делает CI):

```powershell
cargo build --release -p bytetap-app --bin bytetap
```

Готовый файл — `target\release\bytetap.exe`. Тяжёлый нагрузочный тест NFR-5/NFR-6 помечен `#[ignore]` и в обычный прогон не входит.

Сборка с тестовыми хуками — та, которой пользуются смоуки CI (`BYTETAP_TEST_*`, проба цены кадра). Собирается она в отдельный каталог `target/hooks`, чтобы не подменить релизный `target\release\bytetap.exe`, который потом запускают руками и упаковывают:

```powershell
cargo build --release -p bytetap-app --bin bytetap --features test-hooks --target-dir target/hooks
```

Готовый файл — `target\hooks\release\bytetap.exe`.

Feature `test-hooks` добавляет в exe `crates/bytetap-app/src/hooks.rs` (ключи `BYTETAP_TEST_HOOKS`, `BYTETAP_TEST_AUTOSTART`, `BYTETAP_TEST_PANIC`, `BYTETAP_TEST_SCREEN`, `BYTETAP_TEST_JOURNAL`), `probe.rs` (`BYTETAP_TEST_PROBE*`) и переключатели отрисовки в `gpu.rs`; заодно включаются хуки ядра (`bytetap-core/test-hooks`). Без feature этого кода в exe нет вовсе, и переменные `BYTETAP_TEST_*` не читаются: `cargo build --release` и `release.yml` собирают без неё, а `release.yml` проверяет, что строк с префиксом `BYTETAP_TEST` в бинарнике нет. Так устроены сборки начиная со следующей версии после v0.2.0: в самом v0.2.0 хуки в exe есть, но включаются только вместе с `BYTETAP_TEST_HOOKS=1`, и одиночная переменная окружения поведение не меняет. `cargo test` включает feature сама — dev-dependency `bytetap-app` на себя, — поэтому отдельный флаг тестам не нужен.

CI на GitHub Actions повторяет это на Ubuntu и Windows (`ci.yml`), включая `actionlint` и `zizmor`, и складывает `bytetap.exe` в артефакт `bytetap-native-windows-x64`.

## Автоматические проверки нативного интерфейса (U1)

Нативная версия (`crates/bytetap-app`, egui и wgpu, ADR 0003) проверяется теми же командами `npm run check`, а сверх них — своими тестами crate `bytetap-app`:

- `cargo test -p bytetap-app` — unit-тесты (настройки, i18n, лента, кодировки, индекс журнала, перевод времени в событие) и интеграционные: `tests/snapshots.rs` (снимки всех экранов в обеих темах, наименьшего окна 720×560 и ноутбука 1366×768, роли и подписи AccessKit, порядок Tab, Escape, раскладка на 100/125/150 %, кнопки окна внутри шапки при длинных подписях, шаг и запись прокси, радио-пара топологии и ошибка у поля, панель деталей в обеих темах и на вкладках «Текст» и «HEX»), `tests/journal.rs` (просмотр, страницы, карта сессии, комментарий), `tests/journal_failure.rs`, `tests/recording.rs`, `tests/proxy.rs` (прокси из формы на loopback: эмулятор анализатора через прокси к эмулятору ЛИС, `open` с `link`, обе стороны в ленте и журнале, `session_end`, занятый порт прослушивания — ошибка под полем), `tests/input.rs` (кириллица, IME, вставка), `tests/performance.rs` (кадры в простое, при записи и с открытой панелью деталей) `tests/details.rs` (панель деталей: клик по строке, полный фрагмент, HEX, Esc, ↑/↓, Ctrl+A/C, остановка следования, перетаскивание высоты, вытеснение события из кольца, панель в просмотре журнала) и `tests/selection.rs` (выделение строк блоком: клик, Shift+клик, Ctrl+Shift+клик, Ctrl+клик, Shift+↑/↓, Ctrl+A, Ctrl+C с временем и направлением, меню выделения, Esc и следование, фильтр соединения, вытеснение из кольца, роли AccessKit, предел копирования, копирование блока журнала с незагруженных страниц курсором и отмена по «×»);

Снимки шага и записи прокси — `step-proxy-*`, `step-proxy-server-*`, `recording-proxy-*`, `recording-proxy-error-light` и `viewing-proxy-*`; в документацию из них взяты `scenario-proxy` и `recording-proxy`. Раскрытый «Дополнительно» на шаге прокси в окно 1200×800 не помещается и прокручивается: в макете M4-3 он уложен за счёт полей 32px и зазоров 8px, а форма приложения живёт на утверждённом ритме 34px и 12px, и длинные строки FR-8 и брандмауэра переносятся по ширине колонки. Прокрутку заменяет подтягивание к фокусу: тест `tab_brings_the_focused_field_into_view` доводит Tab до «Старт» в окне 1200×800 и проверяет, что кнопка целиком в видимой области. Поведенческие тесты шага прокси — `a_fresh_proxy_form_asks_for_the_target` (пустая цель и «Укажите адрес ЛИС»), `the_proxy_address_errors_keep_their_own_fields` (недоступный интерфейс и неразборчивая цель — каждый под своим полем), `the_proxy_topology_is_a_radio_pair` (группа `RadioGroup`, `toggled`, Space). Адрес источника исходящего соединения (FR-8) проверяется на loopback в `background::source_addr`: тест `the_source_address_of_a_loopback_target_is_loopback`.
- снимки сравниваются только на Linux, где сняты эталоны (программный Vulkan, `mesa-vulkan-drivers`); переснять — `UPDATE_SNAPSHOTS=1 cargo test -p bytetap-app --test snapshots`;
- `cargo clippy -p bytetap-core -p bytetap-app --all-targets --target x86_64-pc-windows-gnu -- -D warnings` — Windows-ветки кода (`windows-sys`, DWM) под линтом;
- `cargo clippy -p bytetap-app --lib --bins -- -D warnings` — приложение в той конфигурации, что уходит в релиз, то есть без feature `test-hooks`: в общей команде `--all-targets` тянет dev-dependency приложения на себя с этой feature, и код под `cfg(not(feature = "test-hooks"))` не собирается вовсе. В CI этот шаг идёт на ubuntu;
- `node scripts/licenses.mjs --check` — `THIRD-PARTY-LICENSES.md` соответствует графу зависимостей для платформы поставки (`x86_64-pc-windows-msvc`) и содержит полные тексты лицензий: одинаковые тексты собраны в группы со списком пакетов, для пакета без файла лицензии взят стандартный текст SPDX из `scripts/license-texts/`; пересобрать — `node scripts/licenses.mjs`.

Job `native-windows` в `ci.yml` собирает `bytetap.exe` из `crates/bytetap-app` и проверяет на `windows-latest`. Сборок две, обе из одного кеша зависимостей: сначала exe с `--features test-hooks` (на нём идут смоуки), в конце — exe без feature, тот же, что уходит в релиз: на нём проверяются запуск без хуков, размер, DLL, иконка, версия и отсутствие строк хуков в байтах. Проверки:

- размер exe ≤ 25 МБ (U1-AC22) и зависимости только из System32 (U1-AC1);
- запуск exe релиза, то есть без хуков, с аппаратным адаптером и с WARP: процесс жив через 15 с, в журнале запуска «интерфейс готов», а на WARP ещё и выбранный `Microsoft Basic Render Driver` (U1-AC2); журналы этих запусков лежат в `smoke/`;
- в байтах exe нет ни одного вхождения префикса `BYTETAP_TEST`, и это не пустой поиск: положительный контроль — строка `BYTETAP_WARP_RETRY` (`gpu::RETRY_ENV`) — обязан находиться, иначе шаг падает. Тот же шаг, что в `release.yml`;
- запуск хуковой сборки с аппаратным адаптером и с WARP: процесс жив, в журнале запуска «интерфейс готов» и выбранный адаптер (U1-AC2);
- смоук паники: системное окно о сбое и запись `паника` в журнале (U1-AC8);
- иконка и версия exe: `FileVersionInfo` отдаёт ProductName `bytetap` и версию из `CARGO_PKG_VERSION` (CompanyName пуст), а `ExtractAssociatedIcon` — иконку, совпадающую с `crates/bytetap-app/assets/icon.ico` (U1-AC1);
- рамка окна: пиксели периметра снимка сверяются с токеном `--bt-border` трижды — на стартовом экране, на экране записи (`BYTETAP_TEST_AUTOSTART` поднимает TCP-сервер) и на том же окне записи без фокуса (фокус забирает блокнот): своя рамка не должна зависеть ни от экрана, ни от активности окна (U1-AC3, U1-AC18); журнал запуска подтверждает, что DWM-рамка скрыта (`DWMWA_COLOR_NONE`), а его строка о скруглении сверяется с атрибутом окна: `DWMWCP_ROUND` — DWM скругляет углы, `DWMWCP_DONOTROUND` на программном растре — углы квадратные;
- запись HL7 по TCP и закрытие окна: журнал заканчивается `session_end` (U1-AC17);
- прокси между анализатором и ЛИС (M4-AC15): хук `BYTETAP_TEST_AUTOSTART=proxy:127.0.0.1:0>127.0.0.1:<порт>:analyzer_client` поднимает прокси на loopback, «ЛИС» — слушатель PowerShell в отдельном задании (порт он сообщает файлом), анализатор шлёт HL7 через прокси, ЛИС отвечает ACK, анализатор получает ACK; после закрытия окна в журнале прокси есть `open` пары с `link` на ЛИС, фрагменты обеих сторон, `mode: proxy` и `session_end`;
- CPU живого процесса: в простое за 10 с — меньше 2 % одного ядра, при записи с потоком 100 фрагментов в секунду — мягкий порог 90 %; оба числа печатаются в журнал CI и лежат в артефакте `bytetap-native-smoke` (`cpu-idle.txt`, `cpu-recording.txt`) (U1-AC24);
- снимки всех экранов в обеих темах из настоящего exe — артефакт `bytetap-native-review-shots` (U1-AC21). Окно ставится по рабочему столу раннера: на `windows-latest` он 1024×720, поэтому снимки exe — 1000×696 (1200×800 не влезает и вышел бы обрезанным), а эталон 1200×800 в точках — те же снимки `egui_kittest` в подпапке `kittest/`.

Экраны для снимков задаёт тестовый хук: `BYTETAP_TEST_SCREEN=<экран>-<тема>` читается, только если задан ещё `BYTETAP_TEST_HOOKS=1`. Остальные тестовые ключи (`BYTETAP_TEST_AUTOSTART`, `BYTETAP_TEST_PANIC`, `BYTETAP_TEST_PROBE*`, `BYTETAP_TEST_JOURNAL`) читаются по тому же правилу — только вместе с `BYTETAP_TEST_HOOKS=1` (`crates/bytetap-app/src/hooks.rs`); без него одиночная переменная окружения поведение exe не меняет, и это проверяет тест. Все хуки собраны под feature `test-hooks`: в релизном exe их нет — ни чтения окружения, ни синтетических экранов, ни пробы цены кадра, — поэтому показать синтетические данные или открыть чужой журнал хуком там нельзя, и `release.yml` проверяет отсутствие строк `BYTETAP_TEST` в бинарнике. Локально хуки включаются сборкой с `--features test-hooks` (см. «Автоматические проверки»): без неё те же переменные окружения ничего не делают. На диск хук не пишет: хранилище настроек он отключает, а тема задаётся только в памяти.

## Ручной смоук v0.2.0 на Windows (нативный интерфейс, U1-AC20)

Выполняет владелец на черновике релиза v0.2.0: `bytetap.exe` из артефакта `bytetap-native-windows-x64` (рядом лежит `THIRD-PARTY-LICENSES.md`). Нужно: Windows 10/11, свободный порт 5000, PowerShell для скриптов из разделов «Источник данных» и, для COM, пара виртуальных портов com0com.

Подготовка:

- [ ] Запустить с чистой папкой настроек `%APPDATA%\bytetap`: окно 1200×800, минимум 720×560, консольного окна нет, рядом с exe нет ни одного файла.
- [ ] В журнале запуска (`%LOCALAPPDATA%\io.github.fgbm.bytetap\logs\bytetap.log`) есть версия, ОС, выбранный адаптер wgpu и «интерфейс готов».
- [ ] Принудительный WARP (`set WGPU_ADAPTER_NAME=basic render`) и машина без аппаратного DX12: окно открывается, журнал запуска называет `Microsoft Basic Render Driver`.

Окно без рамки (U1-AC3, U1-AC26):

- [ ] Шапка тянется мышью за пустое место; двойной клик разворачивает и восстанавливает; кнопки 46×44: свернуть, развернуть/восстановить (иконка меняется), закрыть (красный фон при наведении).
- [ ] Ресайз за все четыре края и углы; курсор меняется на двунаправленный.
- [ ] Развернуть в половину экрана перетаскиванием к краю (снап Windows): окно занимает половину, кнопка показывает «восстановить»; двойной клик по шапке возвращает прежний размер.
- [ ] Рамка 1 px видна сразу после запуска, без смены темы, на стартовом экране, на записи и при просмотре журнала; на белом фоне окно не сливается с ним, на Windows 11 углы скруглены.
- [ ] Рамка остаётся, когда фокус забирает другое окно (например, диалог брандмауэра при первом прослушивании порта): в журнале запуска есть строка «рамка окна: окно неактивно — состояние DWM подтверждено повторно» (первая потеря фокуса за запуск; за ней — столько же строк, сколько было возвращений фокуса, не больше одной).
- [ ] Скругление углов там, где DWM его рисует: на Windows 11 обычное окно со скруглёнными углами, развёрнутое и прижатое к краю (снап) — с квадратными, и линия рамки идёт по углу окна, а не срезает его; на машине с программным растром (ВМ без видеодрайвера) углы квадратные, а в журнале запуска строка «рамка окна: программный растр — углы квадратные (DWMWCP_DONOTROUND)».
- [ ] Второй монитор с другим масштабом (например, 100 % и 150 %): перетащить окно туда — текст и иконки остаются резкими, кнопки окна не съезжают, размер окна в точках не скачет; после перезапуска окно встаёт на запомненное место.
- [ ] Масштаб Windows 125 и 150 %: интерфейс без обрезанного текста и наложений, иконки Lucide не мыльные, рамка окна по-прежнему 1 физический пиксель.

Стартовый экран, три сценария и «Дополнительно» (U1-AC9…AC12): карточки с иконкой, заголовком и описанием, ↑/↓, Enter, последние записи, поля сервера, клиента и COM, автоответ, профили, папка журналов, ошибки под полями.

Запись (U1-AC13…AC17):

- [ ] HL7 по TCP скриптом из раздела «Источник данных: HL7 по TCP»: лента, автоответ, счётчики, «Стоп» с таймером.
- [ ] ASTM по TCP скриптом из раздела «Источник данных: ASTM E1381 по TCP» на профиле «Авто» и «ASTM E1381».
- [ ] COM через пару com0com (раздел «COM-порт на Windows»): обмен идёт в ленту, ответ помечен «автоответ».
- [ ] «Текст»/«HEX», кодировки, фильтр соединений, «↓ N новых», трасса.
- [ ] Комментарий во время записи дописывает `note`; «…» → «Открыть папку журналов» и «Скопировать путь к журналу» работают.
- [ ] Закрытие окна во время записи: сессия останавливается, журнал заканчивается `session_end`, окно закрывается само.
- [ ] Отказ журнала (вынуть флешку): строка «Запись в журнал прервана: …» с двумя действиями, без модального окна.

Просмотр журнала (U1-AC18, U1-AC19):

- [ ] «Журналы» → «Открыть журнал…» и последние записи: шапка с именем файла, анализатором и длительностью, строка о персональных данных.
- [ ] Карта сессии: клик переводит ленту к месту, рамка видимой области двигается; «Комментарий» дописывает `note`; «×» возвращает к сценариям.
- [ ] Журнал на 100+ МБ открывается без чтения целиком; прокрутка в конец (`End`) показывает последнюю строку целиком.
- [ ] Во время записи «Открыть журнал…» недоступна.

Ввод кириллицы и IME (U1-AC27):

- [ ] Русская раскладка в полях «Анализатор», «Комментарий» и в диалоге комментария: буквы, «ё», «№», кавычки-ёлочки; Ctrl+C / Ctrl+V через буфер обмена.
- [ ] Японская или китайская раскладка Windows (IME): композиция видна в поле, окно кандидатов стоит у курсора, а не в углу экрана; подтверждение дописывает слово в поле.

Доступность (U1-AC25):

- [ ] Экранный диктор (Narrator, Win+Ctrl+Enter): Tab обходит шапку, поля, кнопки и ленту в порядке чтения, диктор называет роль и подпись; Enter и Space нажимают кнопку.
- [ ] Фокус всегда виден: кольцо цвета `ctrl` вокруг кнопки, пункта меню, ползунка полосы прокрутки и карточки сценария.
- [ ] Escape закрывает меню «Журналы», «…», «Вид ленты» и диалоги комментария и профиля.

Тема и настройки:

- [ ] Системная тема по умолчанию; переключатель Sun/Moon показывает, в какую тему переведёт, выбор сохраняется после перезапуска.
- [ ] Профиль: «Сохранить», выбрать в списке (поля меняются), «Удалить»; после перезапуска профили на месте.
- [ ] Последние настройки (порт, адрес, порт и скорость COM, анализатор, комментарий, папка, сценарий, вид ленты и кодировка) восстанавливаются после перезапуска.

## Прокси: задержка и нагрузка (NFR-5, NFR-6, M4-AC4, M4-AC12)

Тесты `crates/bytetap-core/tests/proxy_load.rs` помечены `#[ignore]`: они меряют, а не проверяют поведение на каждом push, и на загруженном раннере дают другой результат. Запускаются вручную или по расписанию, а не в `npm run check`:

```bash
cargo test -p bytetap-core --test proxy_load -- --ignored --nocapture --test-threads=1
```

Замер задержки — 2000 обменов «запрос — ответ» по 64 байта на loopback: сначала напрямую к эмулятору ЛИС, потом через прокси к тому же эмулятору. Добавка на направление — половина разницы кругов; пороги из плана — p99 ≤ 2 мс, max ≤ 20 мс.

Замеры 2026-10-22, Linux, debug-сборка, процессор с 16 потоками, loopback:

| Замер | Значение |
|-------|----------|
| Прямой круг, p50 | 18–55 мкс (зависит от загрузки машины) |
| Добавка на направление, p50 | 50–67 мкс |
| Добавка на направление, p99 | 117–153 мкс |
| Добавка на направление, max | 254–369 мкс |
| 8 МиБ в каждую сторону | 0,33–0,70 с |
| Прирост пика памяти (VmHWM) на 8 МиБ в обе стороны | около 50 МБ |

Память в нагрузочном тесте ограничена сверху 128 МБ, а не постоянной величиной: пик задаёт не пересылка (у неё на направление один буфер 16 КиБ), а очередь писателя журнала — канал неограниченный (ADR 0001), и на быстрой пересылке журнал отстаёт на мегабайты строк. Тот же тест проверяет, что `session_end` и счётчики совпадают с отправленным, а журнал содержит ровно те же байты в каждом направлении (сверка длины и хеша FNV-1a по каждому фрагменту).

Пересылка не ждёт журнал — отдельный тест `crates/bytetap-core/tests/proxy_journal_lag.rs`: писатель замедлен хуком `TEST_SYNC_DELAY_MS` на секунду, а обмен через прокси всё равно проходит быстрее 700 мс. Отказ журнала останавливает пересылку — `crates/bytetap-core/tests/proxy_journal_failure.rs`; там же обе топологии: набор закрытия общий для `analyzer_client` и `analyzer_server`.

Очередь писателя ограничена по байтам — `crates/bytetap-core/tests/proxy_backlog.rs`. Тест опускает предел хуком `TEST_MAX_PENDING_BYTES` до 1 МиБ и замедляет писатель `TEST_SYNC_DELAY_MS` на 200 мс, затем гонит 4 МиБ в цель, которая читает и выбрасывает. Ожидается одно `info` с кодом `journal_backlog_warning` (на половине предела), отказ `record` с кодом `journal_backlog`, отсутствие `session_end` и ошибка остановки с этой причиной. Предел 64 МиБ потоком не пройти за разумное время, поэтому и нужен хук.

Тест `crates/bytetap-app/tests/performance.rs::details_panel_frame_cost` помечен `#[ignore]`: он меряет машину, а не проверяет поведение на каждом push.

Панель открыта кликом по строке: вкладка «Текст» раскладывает фрагмент с переносом по ширине, вкладка «HEX» показывает 1024 строки дампа. Понадобится он, если появится фрагмент заметно больше 16 КБ или выделение мышью в нём станет дороже кадра.

## Прокси: подключение к цели (M4-AC6, M4-AC16)

`crates/bytetap-core/tests/proxy_connect.rs` проверяет этап подключения, который сессия отменяет в `select!`:

- отмена `next` (комментарий из интерфейса и закрытие соседней пары) не теряет ни принятое соединение, ни начатое подключение: у задержанной пары есть `open` и обмен — окно подключения открывает хук `TEST_PROXY_CONNECT_DELAY_MS`;
- цель, не ответившая за срок, даёт `proxy_connect_timeout` и не пишет `open`: хук `TEST_PROXY_CONNECT_TIMEOUT_MS` сокращает срок, а задержка изображает молчащую цель;
- несколько входящих соединений подключаются параллельно: четыре пары проходят одно окно, а не четыре подряд.

Хуки глобальны для процесса, поэтому тесты этого файла идут по очереди под одной меткой.

Порядок времени `mono_us` между направлениями — `crates/bytetap-core/tests/proxy_order.rs`: 10⁴ кругов «запрос — ответ» через эхо-ЛИС, проверка, что внутри направления время не убывает, а между направлениями держится причинный порядок. Гарантия записана в [справочнике формата журнала](/reference/session-format), раздел «Порядок строк».

## COM-порт: `socat` на Linux (T-3, M3-AC11)

Тест `crates/bytetap-core/tests/serial.rs` помечен `#[ignore = "requires socat"]`: в обычном `cargo test` его нет, поэтому на машине без `socat` он не падает и не зеленеет молча. Запускается он отдельной командой:

```bash
sudo apt-get install -y socat
cargo test -p bytetap-core --test serial -- --ignored
```

CI на ubuntu ставит `socat` и запускает ровно эту команду с `BYTETAP_REQUIRE_SOCAT=1`. С этой переменной отсутствие `socat` или его отказ — падение теста: COM-режим в CI не должен остаться непроверенным. Без переменной (локальный прогон) тест при отсутствии `socat` печатает «тест пропущен: `socat` не найден» и завершается: пропуск виден в выводе.

Если `socat` есть, тест открывает первый pty как COM-порт, пишет во второй `ENQ` и кадр ASTM E1381 (номер кадра `'1'` — первый после `ENQ`), ждёт `ACK` и проверяет журнал: `peer` — имя порта, `local` пуст, оба направления записаны, ответы `synthetic`, событий `info` и `error` нет — нумерация кадров верная. На pty DTR/RTS не выставляются (у псевдотерминала нет управляющих линий): тест передаёт `--dtr off --rts off`, а `ENOTTY` от этих линий программа не считает ошибкой.

## Прослушка двух COM-портов (M5-AC5, M5-AC8, M5-AC9, M5-AC10)

Прослушка проверяется на трёх уровнях: виртуальная пара в процессе, две пары pty на Linux и ручной смоук владельца на двух USB-адаптерах под Windows.

Виртуальная пара — хук ядра `bytetap_core::transport::virtual_monitor` (только feature `test-hooks`): источник открывает не порты, а концы `tokio::io::duplex`, второй конец держит тест. Так работает `crates/bytetap-core/tests/monitor.rs` в обычном прогоне: обмен в обе стороны побайтно, направление по порту, фрагментация, `open` с `link` на порт ЛИС, пропажа одной стороны закрывает пару и новое `open` со следующим `conn`, «Стоп» даёт одно `close`. Там же на виртуальной паре идут `monitor_journal_failure.rs` (отказ журнала останавливает пересылку) и `monitor_load.rs` (замеры). Хуки глобальны для процесса, поэтому тесты одного файла идут по очереди под одной меткой.

pty на Linux — `crates/bytetap-core/tests/monitor_pty.rs`, `#[ignore = "requires socat"]`: две пары `socat pty,raw,echo=0,link=…`, прослушка открывает псевдотерминалы стороны bytetap, тест играет анализатора и ЛИС на второй стороне. Запуск тот же, что у COM-теста, и CI на ubuntu запускает оба:

```bash
cargo test -p bytetap-core --test monitor_pty -- --ignored
```

Что проверяет pty-тест: `ENQ`, кадр ASTM E1381 и `EOT` доходят до ЛИС байт в байт, два `ACK` и подтверждение HL7/MLLP доходят обратно байт в байт, в журнале `mode: com_monitor`, `settings` с двумя блоками, `open` с `peer` — порт анализатора и `link.role: "lis"` с портом ЛИС. Затем `socat` стороны ЛИС убивается: ведущая сторона pty закрывается, чтение ведомой отдаёт `EIO` — это та же ситуация, что отключённый USB-адаптер. В журнале появляются `error` с кодом `connection_read_failed` или `connection_write_failed` и один `close` с `by: "lis"` и `reason: "error"`, после чего второй `socat` с теми же именами изображает подключённый обратно адаптер: источник открывает оба порта заново, пишется новое `open` с `conn: 2`, и обмен снова проходит.

Замер задержки (`the_monitor_latency_on_pty_stays_within_the_budget`, `#[ignore]`, T-5): 2000 кругов «запрос — ответ» по 64 байта, сначала напрямую через одну пару pty, затем через прослушку; добавка на направление — половина разницы кругов. Пороги NFR-6 — p99 ≤ 2 мс, max ≤ 20 мс.

Замеры 2026-10-23 (повторные, после ревью шага 1), Linux, debug-сборка, `--test-threads=1`:

| Замер | Значение |
|-------|----------|
| Круг напрямую через pty, p50 | 27 мкс |
| Добавка на направление через прослушку на pty, p50 | 38 мкс |
| То же, p99 | 86 мкс |
| То же, max | 434 мкс |
| 8 МиБ в каждую сторону через виртуальную пару | 0,25 с |

Замер на виртуальной паре (`crates/bytetap-core/tests/monitor_load.rs`, `--ignored`) показывает добавку самой пересылки, без драйвера: p50 2 мкс, p99 9 мкс, max 74 мкс на направление.

Замер с порогами не гоняется на каждом push: в CI запускается только функциональный pty-тест (`--skip the_monitor_latency`), потому что пороги времени на общем раннере дают ложные падения. Замер запускается вручную:

```bash
cargo test -p bytetap-core --test monitor_pty -- --ignored the_monitor_latency
```

**Задержка на Windows не гарантирована.** Там порт открыт синхронным handle: `ReadFile` и `WriteFile` одного устройства драйвер выполняет по очереди, а таймаут отсчитывается по системному тику — по умолчанию 15,6 мс. На время сессии прослушки разрешение таймера поднимается до 1 мс (`timeBeginPeriod(1)`, в журнале `info` с кодом `timer_resolution`), после чего ожидается добавка порядка миллисекунды, но справедливость самой блокировки Windows не обещает: запись может прождать текущее чтение. Границу NFR-6 на Windows даёт только overlapped I/O, которого сейчас нет; это риск, записанный в дополнении к [ADR 0002](/dev/adr/0002-serial-port), а числа на Windows не заявляются до ручного смоука.

Нагрузка (`eight_megabytes_go_both_ways`, `#[ignore]`, NFR-5): 8 МиБ в каждую сторону одновременно, счётчики и `session_end` совпадают с отправленным, журнал сверяется по длине и хешу FNV-1a по каждому направлению, прирост пика памяти ограничен 128 МБ — как в нагрузочном тесте прокси, потому что пик задаёт очередь писателя журнала, а не пересылка.

```bash
cargo test -p bytetap-core --test monitor_load -- --ignored --nocapture --test-threads=1
```

Ручной смоук на настоящих портах под Windows (M5-AC5, M5-AC9). Виртуальных COM-портов на `windows-latest` нет, `com0com` — драйвер уровня ядра и в CI не ставится, поэтому автоматической проверки настоящего COM в прослушке на Windows нет: в CI проверяются сборка, unit-тесты и сквозной смоук на виртуальной паре. Числа задержки на Windows заявляются только после этого смоука владельца на двух USB-адаптерах; если он не пройден, проверка уходит в [бэклог](/dev/backlog), а числа не заявляются.

Сквозной смоук в CI идёт через exe с тестовыми хуками: `BYTETAP_TEST_AUTOSTART=monitor:virtual` поднимает прослушку на виртуальной паре, а «анализатор» и «ЛИС» играет сама программа обменом ASTM E1381 (`ENQ` → `ACK`, кадр `STX…ETX` → `ACK`, `EOT`). Шаг `native-windows` закрывает окно штатно и проверяет журнал сессии: `mode: com_monitor`, `open` с `link` на порт ЛИС, `data` обеих сторон, `session_end`; в журнале запуска — «интерфейс готов». Экраны прослушки снимаются там же вместе с остальными. Настоящий COM и задержка на Windows — только этот ручной смоук, автоматической проверки нет.

- [ ] Два USB-RS232 адаптера, линия разрезана: анализатор на одном конце, ЛИС или преобразователь RS232–Ethernet на другом.
- [ ] `bytetap-cli capture --monitor COM3 --to COM4 --baud 9600 --format 8N1`: печатается «Прослушка: COM3 ⇄ COM4 (9600 8N1, поток none)», журнал создан.
- [ ] Обмен анализатора с ЛИС проходит как без bytetap: прибор получает ответы, ЛИС видит записи; в ленте оба направления, `data` без изменений.
- [ ] В журнале `mode: com_monitor`, `open` с `peer: "COM3"` и `link` на `COM4`, `settings` с двумя блоками, `session_end` со счётчиками.
- [ ] Выдернуть USB-адаптер стороны ЛИС: в ленте ошибка «COM4 пропал — жду подключения», в журнале `error` и `close` с `by: "lis"`. Вставить адаптер обратно: новое `open` с другим `conn`, обмен продолжается.
- [ ] Повторить с потоком `rtscts` и с `xonxoff`: программа предупреждает, что линии сквозь bytetap не передаются; с `xonxoff` байты `0x11` и `0x13` из обмена исчезают — это ожидаемо и объяснено в руководстве.
- [ ] Разрешение таймера: в журнале запуска и в журнале сессии есть `info` с кодом `timer_resolution`; `ClockRes` (Sysinternals) во время сессии показывает текущее разрешение 1 мс, после остановки — прежнее. Проверить дважды: с открытым окном bytetap и со свёрнутым — на Windows 11 свёрнутое окно иначе получает понижённое разрешение (программа просит `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`, но проверить это надо глазами).
- [ ] Задержка `ENQ → ACK` через bytetap против прямой линии: на одном и том же обмене (анализатор отвечает ЛИС, bytetap в разрыве и вне его) разница не больше пары миллисекунд; числа записать сюда.
- [ ] HL7-сообщение 3–5 КБ на 9600 бод проходит без пауз и без потерь: `WriteFile` с окном 50 мс не рвёт длинную передачу, а фрагмент доходит целиком (в журнале `data` обеих сторон совпадают с отправленным). Пара не закрывается, если ЛИС перестала читать на несколько секунд, — на пути данных срока нет; в CI это проверяет pty-тест `the_pair_survives_a_lis_that_does_not_read`.
- [ ] «Стоп» во время длинной передачи: журнал кончается `close` и `session_end`, а байты, которые драйвер принял в пределах 100 мс после остановки, попадают в журнал — это проверяет тест `an_answer_sent_before_stop_is_in_the_journal` (хук `TEST_HOLD_WRITE_REPORT`). Граница гарантии — в [архитектуре](/dev/architecture): после льготы поток писателя может дописать текущее окно `port.write` (до 50 мс линии на Windows), и эти байты уходят в линию, но не в журнал.
- [ ] Открыть папку журналов из интерфейса во время записи и закрыть окно bytetap: порт освобождается сразу, следующий старт его открывает (handle не наследуется `explorer`).

## COM-порт на Windows: ручной сценарий com0com (T-3)

Автоматического теста на Windows нет: пара виртуальных портов ставится драйвером, а его установка в CI не автоматизируется. Проверка выполняется вручную на сборке из CI. `bytetap-cli` в артефакт не входит: соберите его из исходников (`cargo build --release -p bytetap-cli`, файл `target\release\bytetap-cli.exe`) или пройдите те же шаги в интерфейсе — сценарий «Кабель COM-порта» в чек-листе выше.

- [ ] Установить [com0com](https://sourceforge.net/projects/com0com/) и создать пару портов, например `COM5` ↔ `COM6` (в свежих сборках com0com номера задаются в Setup).
- [ ] Запустить `bytetap-cli ports`: в списке есть оба порта, у пары com0com описание — имя порта.
- [ ] Запустить `bytetap-cli capture --serial COM5 --baud 9600 --format 8N1 --responder astm`.
- [ ] Открыть `COM6` терминалом (PuTTY, RealTerm) с теми же 9600 8N1.
- [ ] Отправить `ENQ` (`0x05`): в терминал приходит `ACK` (`0x06`), в ленте `capture` — фрагмент анализатора и синтетический ответ.
- [ ] Отправить кадр `STX 1H|\^&… ETX <сумма> CR LF` (номер кадра — ASCII `1`, первый после `ENQ`) с верной суммой: приходит `ACK`; с неверной — по умолчанию тоже `ACK` и `error` в журнале, с `--astm-nak` — `NAK` (`0x15`).
- [ ] Нажать «Стоп»: соединение закрывается событием `close`, журнал заканчивается `session_end`.
- [ ] Отключить пару com0com во время записи: в журнале `close` и `error`, сессия продолжает работать; после включения пары порт переоткрывается сам, в журнале новое `open` с следующим `conn`.
- [ ] Проверить `bytetap-cli verify` на получившемся журнале: ошибок нет.

## Источник данных: HL7 по TCP (PowerShell)

Если под рукой нет анализатора и `bytetap-testkit` (он собирается из исходников), синтетическое сообщение шлёт PowerShell той же машины. Нужен запущенный «Анализатор подключается ко мне» на порту 5000 и автоответ «HL7/MLLP» или «Авто»; скрипт печатает ACK.

```powershell
$client = [System.Net.Sockets.TcpClient]::new("127.0.0.1", 5000)
$client.ReceiveTimeout = 5000
$stream = $client.GetStream()
$msh = "MSH|^~\&|ANALYZER|LAB|LIS||20261019101500||ORU^R01|MSG0001|P|2.3.1"
$pidSegment = "PID|1||000001||PATIENT^TEST"
# Рамка MLLP: 0x0B, сообщение с CR, 0x1C, CR
$msg = [Text.Encoding]::ASCII.GetBytes("$([char]11)$msh`r$pidSegment`r$([char]28)`r")
$stream.Write($msg, 0, $msg.Length)
$buffer = New-Object byte[] 4096
$read = $stream.Read($buffer, 0, $buffer.Length)
[Text.Encoding]::ASCII.GetString($buffer, 0, $read)
$client.Close()
```

В ленте появятся `#1 подключился`, фрагмент анализатора с глифами `‹VT›`, `‹CR›`, `‹FS›` и ответ со словом «автоответ»; после закрытия соединения — `#1 отключился`. Для профиля «Без ответов» ACK не придёт — это ожидаемо.

## Источник данных: ASTM E1381 по TCP (PowerShell)

ASTM идёт тем же портом 5000: профиль «Авто» узнаёт его по первому байту `ENQ` (`0x05`). Нужен автоответ «ASTM E1381» или «Авто». Скрипт проводит полный обмен — `ENQ`, кадр записи `'1'` с верной суммой, `EOT` — и читает оба `ACK`.

```powershell
$client = [System.Net.Sockets.TcpClient]::new("127.0.0.1", 5000)
$client.ReceiveTimeout = 5000
$stream = $client.GetStream()

# Запись: три сегмента, каждый заканчивается CR
$segments = "H|\^&|||ANALYZER^1|||||||||P|1`rP|1||PATIENT^TEST`rL|1|N`r"
# Сумма считается по байтам от номера кадра до ETX включительно, по модулю 256
$body = [Text.Encoding]::ASCII.GetBytes("1" + $segments + [char]3)
$sum = 0
foreach ($b in $body) { $sum = ($sum + $b) % 256 }

$stream.Write([byte[]]@(0x05), 0, 1); $null = $stream.ReadByte()   # ENQ → ACK
$stream.Write([byte[]]@(0x02), 0, 1)                                 # STX
$stream.Write($body, 0, $body.Length)                               # 1 … ETX
$checksum = [Text.Encoding]::ASCII.GetBytes(("{0:X2}" -f $sum) + "`r`n")
$stream.Write($checksum, 0, $checksum.Length)                      # сумма 2C, CR LF
$null = $stream.ReadByte()                                          # ACK на кадр
$stream.Write([byte[]]@(0x04), 0, 1)                                 # EOT, ответа нет
$client.Close()
```

Для этих сегментов сумма — `2C`: `0x31 + 0x48 … + 0x0D + 0x03 = 0x12C`, по модулю 256 — `0x2C`. Если править текст записи, сумму нужно пересчитать — иначе кадр подтвердится, но в журнале появится `error` о неверной сумме (а с «NAK на неверную сумму» ответ будет `NAK`, `0x15`).
