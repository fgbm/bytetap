# Релизы

## Что поставляется

Основной формат поставки — переносимый `bytetap.exe`: его копируют на ноутбук инженера и запускают без установки. С v0.2.0 exe собирается из `crates/bytetap-app` — нативное приложение на egui и wgpu, без WebView2, .NET и Visual C++ Redistributable. Установщик (NSIS/MSI) пока не собирается.

В zip релиза входят `bytetap.exe`, `README.md`, `LICENSE`, `THIRD-PARTY-LICENSES.md` и `SHA256SUMS`. Имя архива — `bytetap-v<версия>-windows-x64.zip`, имя exe внутри архива — `bytetap.exe`.

WebView2 в поставке больше нет: в v0.1.0 это был системный компонент, который Tauri-версия брала из Windows, а на офлайн-ноутбуках он бывал слишком старым. Нативная версия рисует окно сама, зависимость exe — только системные DLL Windows (проверяется в CI по `dumpbin /dependents`).

## Процесс выпуска

1. **Подготовка.** Версия в `[workspace.package]` корневого `Cargo.toml` — `0.2.0`; от неё же берут версию `bytetap-app` и `bytetap-cli` и строка версии в журнале запуска. `CHANGELOG.md` согласован с этой версией: раздел релиза заполнен, `Unreleased` пуст, ссылки сравнения на месте.
2. **Проверка workflow без тега.** Пока тега нет, релизную сборку можно прогнать вручную: `gh workflow run Release --ref native-ui`. Собираются те же zip и `SHA256SUMS`, job `publish` не запускается — по тегу он и только он создаёт черновик.
3. **Тег.** После зелёного CI на `main` владелец ставит аннотированный тег `v0.2.0` на коммит релиза и пушит его: `git tag -a v0.2.0 -m "bytetap v0.2.0"` и `git push origin v0.2.0`. Тег запускает `release.yml`; версия тега обязана совпадать с `Cargo.toml`, иначе workflow падает на шаге «Сверить тег с версией».
4. **Сборка.** Workflow собирает exe на `windows-latest` (`cargo build --release -p bytetap-app --bin bytetap`), проверяет размер (≤ 25 МБ, NFR-7) и зависимости только из `System32` (U1-AC1), сверяет `THIRD-PARTY-LICENSES.md` с графом зависимостей, кладёт `target/release/bytetap.exe` в zip вместе с `README.md`, `LICENSE` и `THIRD-PARTY-LICENSES.md` и считает `SHA256SUMS`.
5. **Черновик.** Второй job проверяет контрольную сумму и создаёт **черновик** релиза через `gh release create --draft --verify-tag --generate-notes`. Публикации на этом шаге нет: релиз виден только владельцу и команде.
6. **Смоук владельца.** Владелец скачивает zip из черновика, проверяет `SHA256SUMS`, запускает exe на Windows, проходит чек-лист из `docs/dev/testing.md` (старт, обмен, стоп, просмотр журнала, темы, профили) и сверяет версию в имени архива и в журнале запуска (`%LOCALAPPDATA%\io.github.fgbm.bytetap\logs\bytetap.log`).
7. **Публикация.** Владелец правит заметки релиза и нажимает «Publish release» в GitHub. После публикации обновляются ссылки `releases/tag/v0.2.0` в README и в `docs/guide/install.md`, и объявляется релиз.

## SmartScreen и подпись

До M6 релизы выходят **без подписи кода**: сертификат в бюджет проекта не входит. Поэтому каждый новый exe встречает SmartScreen предупреждением «Windows защитила Ваш компьютер»; это ожидаемое поведение, а не признак заражения. Проверить файл можно по `SHA256SUMS` из релиза. Пользовательская инструкция — `docs/guide/smartscreen.md`.

Подпись, установщик и автообновления — этап M6. До него release-workflow не подписывает exe, не публикует релиз автоматически и не трогает `latest`.
