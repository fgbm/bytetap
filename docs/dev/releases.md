# Релизы

Страница описывает выпуск версии `X.Y.Z`: что поставляется, в каком порядке идёт выпуск и что проверяет владелец. Конкретные версии и их состав — в [дорожной карте](/dev/roadmap), требования к поставке — в [требованиях](/dev/requirements) (NFR-2, NFR-7, DOC-5).

## Что поставляется

Основной формат поставки — переносимый `bytetap.exe`: его копируют на ноутбук инженера и запускают без установки и без прав администратора. exe собирается из `crates/bytetap-app` — нативное приложение на egui и wgpu: WebView2, .NET и Visual C++ Redistributable ему не нужны, зависимость — только системные DLL Windows (проверяется в CI по `dumpbin /dependents`). Установщик (NSIS/MSI) пока не собирается.

В zip релиза входят `bytetap.exe`, `README.md`, `LICENSE` и `THIRD-PARTY-LICENSES.md`, рядом с архивом лежит `SHA256SUMS`. Имя архива — `bytetap-v<X.Y.Z>-windows-x64.zip`, имя exe внутри архива — `bytetap.exe`.

## Процесс выпуска

Порядок один и тот же для любой версии: тег, черновик, проверка владельца, публикация. Публикация идёт только после проверки черновика, а не вместе с тегом.

1. **Подготовка.** Версия в `[workspace.package]` корневого `Cargo.toml` — `X.Y.Z`; от неё же берут версию `bytetap-app` и `bytetap-cli` и строка версии в журнале запуска. `CHANGELOG.md` согласован с этой версией: раздел `X.Y.Z` заполнен, `Unreleased` пуст, ссылки сравнения на месте. CI на `main` зелёный, коммит релиза отмечен в истории.
2. **Тег.** Владелец ставит аннотированный тег на коммит релиза и пушит его:

   ```sh
   git tag -a vX.Y.Z -m "bytetap vX.Y.Z"
   git push origin vX.Y.Z
   ```

   Тег запускает `release.yml`. Версия тега обязана совпадать с `Cargo.toml`, иначе workflow падает на шаге «Сверить тег с версией». Без тега workflow можно прогнать вручную (`gh workflow run Release --ref main`): соберутся те же артефакты, но job `publish` не запустится — он идёт только на `push` по тегу.
3. **Сборка и черновик.** Workflow собирает exe на `windows-latest` (`cargo build --release --locked -p bytetap-app --bin bytetap`), проверяет размер (≤ 25 МБ, NFR-7) и зависимости только из `System32` (U1-AC1), сверяет `THIRD-PARTY-LICENSES.md` с графом зависимостей, кладёт `target/release/bytetap.exe` в zip вместе с `README.md`, `LICENSE` и `THIRD-PARTY-LICENSES.md` и считает `SHA256SUMS`. Второй job проверяет контрольную сумму и создаёт **черновик** релиза через `gh release create --draft --verify-tag --generate-notes`. На этом шаге ничего не публикуется: черновик виден только владельцу и команде.
4. **Проверка.** Владелец скачивает zip из черновика, проверяет `SHA256SUMS`, запускает exe на Windows и проходит чек-лист из [тестирования](/dev/testing): старт, обмен, стоп, просмотр журнала, темы, профили. Версия в имени архива, в заголовке окна и в журнале запуска (`%LOCALAPPDATA%\io.github.fgbm.bytetap\logs\bytetap.log`) должна совпадать с версией тега. Если проверка нашла ошибку, черновик не публикуется: исправление идёт новым коммитом, тег переносится или ставится заново.
5. **Публикация.** Владелец правит заметки релиза и нажимает «Publish release» в GitHub. После публикации обновляются ссылки `releases/tag/v<X.Y.Z>` в `README.md` и в `docs/guide/install.md`, и релиз объявляется.

## SmartScreen и подпись

До M6 релизы выходят **без подписи кода**: сертификат в бюджет проекта не входит. Поэтому каждый новый exe встречает SmartScreen предупреждением «Windows защитила Ваш компьютер»; это ожидаемое поведение, а не признак заражения. Проверить файл можно по `SHA256SUMS` из релиза. Пользовательская инструкция — `docs/guide/smartscreen.md`.

Подпись, установщик и автообновления — этап M6. До него release-workflow не подписывает exe, не публикует релиз автоматически и не трогает `latest`.
