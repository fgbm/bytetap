# M1 — ядро: TCP-сервер, журнал, автоответчик HL7/MLLP

Цель этапа — снять обмен HL7-анализатора без интерфейса: `bytetap-cli capture` слушает порт, пишет журнал сессии и отвечает анализатору ACK, а `bytetap-cli verify` и `bytetap-cli note` работают с готовым журналом. Интерфейса на этом этапе нет, ядро проверяется интеграционными тестами на loopback.

## Шаги

Каждый шаг — отдельная задача реализации и отдельный цикл ревью.

- [x] Шаг 1. Журнал: модель событий, писатель, экранирование `text`, формат и его документ. Ревью 1: исправлено в коммите da05dea.
- [x] Шаг 2. MLLP и HL7 ACK как sans-IO автомат. Ревью 1: исправлено в коммите c649fc7.
- [x] Шаг 3. Сессия и TCP-сервер, `bytetap-cli capture`, testkit-эмулятор HL7, интеграционные тесты. Ревью 1: исправлено в коммитах efa46ca и aad17aa.

## Архитектура

Решение этапа, на которое опираются шаги.

- Модули `bytetap-core`: `journal` (события, сериализация, писатель, читатель), `text` (экранирование FR-22), `responder` (трейт `Responder` с методами `feed(&[u8], now) -> Vec<Action>` и `finish(now) -> Vec<Action>`, `Action::{Send(Vec<u8>), Event(...)}`; реализации `NoResponder` и `Hl7Mllp`; `ControlIdSource` — общий на сессию счётчик `MSH-10`), `transport::tcp` (сервер), `session` (актор: старт и стоп, broadcast `SessionEvent`, подписчики).
- Горячий путь: прочитали фрагмент → взяли метки `mono_us` (от `Instant` старта сессии) и `t` (`chrono::Local`, RFC 3339 с микросекундами и смещением) → отдали фрагмент автоответчику → отправили ответ → положили события в канал журнала. Журнал не блокирует чтение.
- Писатель журнала — отдельная задача и канал mpsc. Канал неограниченный либо с большим лимитом; выбор и обоснование фиксируются в ADR при реализации шага 1 (неограниченный канал проще и не создаёт backpressure в горячий путь, но требует оценки памяти на NFR-5).
- Пачка пишется группой: все накопленные события → `write` → один `flush` → один `sync_data` (FR-20). Пачка ограничена сверху, чтобы журнал не задерживался на медленном диске.
- Ошибка в соединении закрывается вместе с этим соединением и пишется событием `error`; сессия продолжается (NFR-5).

## Критерии приёмки

- [x] M1-AC1. Формат журнала `bytetap-session/1` описан в `docs/reference/session-format.md` (все типы событий: `session`, `open`, `data`, `close`, `error`, `note`, `session_end`; поля, типы, обязательность, правила `text`, `synthetic`, `mono_us`, `t`, `conn`, `dir`) и в JSON Schema `docs/public/schema/bytetap-session-1.schema.json`; строки, которые пишет ядро, проходят валидацию по схеме в тесте.
- [x] M1-AC2. Имя файла — `bytetap-<YYYYMMDD-HHMMSS>-<режим>.jsonl`, папка по умолчанию `<home>/Documents/bytetap` (crate `dirs`, `home_dir()`; не known folder, чтобы Known Folder Move не увёз журналы в OneDrive), занятое имя получает суффикс `-2`…`-99` (FR-19). Папку переопределяет `capture --log-dir DIR` (M1-AC15), в библиотеке путь задаётся аргументом `Journal::create`.
- [x] M1-AC3a. Первая строка — `session` с полями FR-21 (`app_version` из `Cargo.toml`, `host.os`), и она ровно одна; `note` дописывается в конец файла, начало файла не переписывается (FR-23).
- [x] M1-AC3b. Последняя строка при штатной остановке — `session_end` со статистикой (появится вместе с сессией в шаге 3).
- [x] M1-AC4. Событие `data`: `b64` — исходные байты фрагмента без склейки; `text` по правилам FR-22 (печатные ASCII 0x20–0x7E как есть, кроме `<`, который пишется `<x3C>`; перечисленные управляющие как `<STX>` и т. д.; остальные как `<xHH>` в верхнем регистре); `len`; `synthetic`.
- [x] M1-AC5. Unit-тесты экранирования: все управляющие символы из FR-22, все байты 0x00–0xFF, символ `<` в данных (экранируется он или нет — решение фиксируется в `session-format.md`, чтобы `text` читался однозначно), не-ASCII байты.
- [x] M1-AC6. Групповая фиксация: писатель делает один `flush` и один `sync_data` на пачку; тест: N событий → файл содержит N строк валидного JSON в порядке отправки.
- [x] M1-AC7 (T-4). Тест устойчивости: дочерний процесс `bytetap-cli` пишет журнал под нагрузкой, его убивают (SIGKILL / TerminateProcess), после чего каждая строка, кроме, возможно, последней, — валидный JSON по схеме.
- [x] M1-AC8 (FR-16). MLLP: выделение сообщений по рамке `0x0B … 0x1C 0x0D` при любом разбиении потока на фрагменты (proptest); мусор вне рамки не ломает автомат, о его блоках сообщает событие `info`. Журнальная часть (превращение событий автоответчика в строки журнала) — в AC13 (шаг 3).
- [x] M1-AC9 (FR-16). HL7 ACK: разделители берутся из MSH-1/MSH-2 входящего; MSH-3/4 и MSH-5/6 переставлены; время отправки; тип `ACK^<событие из MSH-9>`; новый MSH-10 не длиннее 20 знаков из общего на сессию счётчика; MSH-11 и MSH-12 копируются из входящего, пустой MSH-11 → `P`; `MSA|AA|<MSH-10 входящего>`; кодировка ACK — ASCII; входящий ACK не подтверждается. Unit-тесты: стандартные и нестандартные разделители, отсутствующие поля, MSH-9 без события, неразбираемое сообщение с извлекаемым MSH-10 → `MSA|AE` на разделителях этого MSH, без MSH-10 → ответа нет. Журнальная часть — в AC13 (шаг 3).
- [x] M1-AC10 (FR-18). HL7-запросы (например `QRY^Q02`) подтверждаются только ACK, без DSR.
- [x] M1-AC11 (FR-1). TCP-сервер: слушает адрес:порт, несколько последовательных и параллельных соединений за сессию с нумерацией `conn`, события `open`/`close` с `peer`/`local`, `by`, `reason`.
- [x] M1-AC12 (FR-4). Ответы автоответчика пишутся с `dir: lis_to_analyzer` и `synthetic: true`.
- [x] M1-AC13 (T-2). Интеграционные тесты на loopback: эмулятор анализатора из `bytetap-testkit` (HL7/MLLP, режимы: целым сообщением, побайтно, случайная нарезка; переподключение) ↔ сессия; проверяется, что склейка `b64` по направлению анализатор→ЛИС побайтно равна отправленному, эмулятор получил ACK на каждое сообщение с правильным MSA-2, число соединений и события `open`/`close` совпадают.
- [x] M1-AC14 (NFR-6). Пересылка ответа не ждёт журнал: тест, где писатель журнала искусственно замедлен, а ACK приходит эмулятору в пределах таймаута.
- [x] M1-AC15. `bytetap-cli capture --listen 0.0.0.0:5000 --responder hl7|none [--log-dir DIR] [--analyzer TEXT] [--note TEXT]` печатает путь к журналу и краткую ленту (время, стрелка, conn, `text`), Ctrl+C → штатная остановка с `session_end`. `bytetap-cli verify <file>` проверяет журнал по схеме и печатает статистику; `bytetap-cli note <file> TEXT` дописывает событие `note`.
- [x] M1-AC16. Тестовые журналы и фикстуры — только синтетические (`ANALYZER`, `LIS`, `PATIENT^TEST`), лежат в `tests/fixtures/`.
- [x] M1-AC17. `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` и `cargo test --workspace` зелёные на ubuntu и windows в CI; `bytetap-core` по-прежнему без tauri.
- [x] M1-AC18. В `docs/guide` есть страница «Запуск из командной строки» с примером `capture` и `verify` (временная, до M2), `CHANGELOG.md` в разделе Unreleased дополнен.

## Вне рамок

- TCP-клиент (FR-2).
- ASTM (FR-17).
- Режим «Авто» (FR-15).
- Прокси (FR-5…FR-8).
- RS232 (FR-9…FR-13).
- Интерфейс (M2).
- Ответы на запросы анализатора, `DSR` (FR-18).
