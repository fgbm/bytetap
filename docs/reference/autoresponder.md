# Автоответчик

Автоответчик отвечает анализатору, чтобы тот не повторял сообщения и продолжал передачу (FR-3). В первой версии он подтверждает обмен на транспортном уровне и не формирует ответов на запросы (FR-18).

Профили (FR-14):

| Профиль | Состояние |
|---------|-----------|
| `hl7_mllp` | HL7/MLLP, описан ниже |
| `none` | «Без ответов»: байты пишутся в журнал, ответов нет |
| `astm_e1381` | ASTM E1381, описан ниже |
| `auto` | «Авто»: протокол по первому байту соединения, описан ниже |

Автоответчик не знает ни про сокеты, ни про файл журнала: он получает прочитанные байты и возвращает, что отправить и что записать в журнал. Поэтому его поведение одинаково для TCP и для COM-порта, а проверяется оно без сети. Фрагменты потока он получает через `feed(&[u8], now)`, а закрытие соединения — через `finish(now)`: в отличие от `reset` тот не выбрасывает недособранное состояние молча.

Время автомату передаёт сессия, он сам часов не читает: поэтому тесты детерминированы. У автомата есть ещё необязательный срок — `poll_timeout(now)`. Если он не пуст, сессия держит его в ожидании и по истечении будит автомат пустым `feed(&[], now)`: тот сообщает в журнал о недособранном состоянии и возвращается в ожидание. Срок нужен ASTM; HL7/MLLP, «Авто» до решения и «Без ответов» его не задают.

## HL7/MLLP (FR-16)

### Рамка

Сообщение HL7 передаётся между двумя байтами рамки:

- начало — `0x0B` (`VT`), в записи журнала `<VT>`;
- конец — `0x1C 0x0D` (`FS` `CR`), в записи журнала `<FS><CR>`.

ACK отправляется в такой же рамке: `0x0B` … `0x1C 0x0D`.

Поток может быть разрезан на фрагменты как угодно, вплоть до побайтовой передачи: автомат собирает сообщение из любого числа фрагментов, и `0x1C`, и `0x0D` могут прийти в разных фрагментах.

Правила разбора рамки:

- `0x1C`, за которым идёт не `0x0D`, — обычный байт сообщения; рамка закрывается только парой `0x1C 0x0D`.
- `0x0B` внутри незакрытой рамки означает потерю предыдущего сообщения: в журнал пишется событие `error` («incomplete MLLP frame dropped»), и с этого байта начинается новая рамка.
- Пустая рамка (`0x0B` сразу за ней `0x1C 0x0D`) — неразбираемое сообщение: событие `error`, ответа нет.
- Несколько `0x0B` подряд, когда рамка ещё пуста, — не ошибка: прибор мог начать сообщение заново, терять нечего.
- Размер незакрытой рамки ограничен 16 МиБ. При превышении буфер сбрасывается с событием `error`, и до следующего `0x0B` байты считаются мусором вне рамки. Ограничение нужно, чтобы поток без закрывающей пары не съел память (NFR-5).

### Байты вне рамки

Байты вне рамки (`<VT>` ещё не пришёл, или рамка уже закрыта) ответа не вызывают. Они не теряются: журнал получает их как обычные данные (`data`), но в протоколе автоответчика они мусор.

О блоке такого мусора пишется одно событие `info` с числом байтов — когда блок заканчивается, то есть на открывающем `0x0B` следующей рамки. Пока блок не закончился, событие не пишется: длина блока ещё неизвестна. Хвост мусора после последней рамки заканчивается вместе с соединением и сообщается при закрытии — об этом ниже.

Пример: `junk` + рамка с `ORU^R01` дают `info` о 4 байтах мусора и один ACK. Мусор в ответ не попадает.

### Разбор сообщения

Сообщение делится на сегменты по `CR` (`0x0D`). Как разделитель сегментов принимаются также `LF` (`0x0A`) и `CR LF`: некоторые приборы шлют так. Пустые сегменты отбрасываются.

Первым сегментом должен быть `MSH`:

- `MSH-1` — четвёртый байт сегмента, печатный ASCII кроме пробела;
- `MSH-2` — разделитель компонентов, повторов, escape и субкомпонентов, столько знаков, сколько есть (в HL7 их четыре, порядок: компонент, повтор, escape, субкомпонент); все байты `MSH-2` — печатный ASCII. Короткий `MSH-2` допустим: чего в нём нет, тем ACK не пользуется. `MSH-2` копируется в ACK байтово как есть.

Событие-триггер берётся из `MSH-9.2` — второго компонента `MSH-9` по компонентному разделителю.

### ACK

| Поле ACK | Значение |
|----------|----------|
| `MSH-1`, `MSH-2` | байтово из входящего `MSH-1`/`MSH-2` |
| `MSH-3`, `MSH-4` | из входящих `MSH-5`, `MSH-6` (перестановка) |
| `MSH-5`, `MSH-6` | из входящих `MSH-3`, `MSH-4` (перестановка) |
| `MSH-7` | время отправки: `YYYYMMDDHHMMSS±ZZZZ`, местное время со смещением от UTC |
| `MSH-8` | пусто |
| `MSH-9` | `ACK` или `ACK<компонент><событие из MSH-9.2>` |
| `MSH-10` | новый идентификатор: `BT`, время отправки и счётчик, ровно 20 знаков печатного ASCII |
| `MSH-11` | байтово из входящего `MSH-11`; если его нет, оно пусто или не ASCII — `P` |
| `MSH-12` | байтово из входящего `MSH-12`; если его нет — пусто |
| `MSA-1` | `AA` — сообщение принято |
| `MSA-2` | байтово из входящего `MSH-10` |

ACK состоит из двух сегментов, `MSH` и `MSA`, каждый заканчивается `CR`; `CR` заканчивает и весь текст ACK. Поля `MSH` пишутся все до `MSH-12`: пустые остаются на своих местах, поэтому строка MSH может заканчиваться разделителем поля.

`MSH-11` копируется, а не придумывается: если прибор прислал `T`, ACK будет с `T`. Подстановка `P` — только когда входящее поле пустое: пустая процедура обработки выглядит как ошибка формата.

`MSH-10` ACK: `BT` + время отправки `YYMMDDHHMMSS` + счётчик из шести цифр, например `BT261019101530000001`, — ровно 20 знаков. Счётчик один на сессию: его передают в конструктор автоответчика, поэтому все соединения берут номера из него и `MSH-10` не повторяется между ними, а время отсекает совпадения между секундами. Шести цифр хватает на миллион ответов в секунду.

Известное ограничение: счётчик начинается заново с каждой сессией, поэтому если новую запись запустить в ту же секунду, в которую отвечала предыдущая, `MSH-10` двух ответов совпадут. Внутри сессии совпадений нет, а прибор сопоставляет ACK с последним отправленным сообщением, так что на M1 это осознанно оставлено как есть: сквозной счётчик между запусками потребовал бы хранить состояние на диске.

Время `MSH-7` берётся из того момента, когда автоответчик получил сообщение; часы ему передаёт сессия. Поэтому тесты детерминированы.

### Кодировка ACK — ASCII

ACK всегда ASCII. Копируемое поле переносится байтово только тогда, когда все его байты — печатный ASCII (`0x20`–`0x7E`). Иначе поле остаётся пустым, а в журнал пишется событие `info`: «MSH-3 is not ASCII: the field is left empty in the ACK». Замены на `?` нет: искажённое значение хуже пустого, потому что выглядит достоверным.

То же правило действует для особых случаев:

- `MSH-9.2` не ASCII — тип ACK остаётся `ACK` без события, событие `info`;
- `MSH-10` входящего не ASCII — `MSA-2` пустой, событие `info`;
- `MSH-10` входящего пустой — `MSA-2` пустой, событие `info`;
- компонентного разделителя нет (пустой `MSH-2`) — тип ACK остаётся `ACK`, событие в `MSH-9` не ставится.

### Входящие подтверждения

Сообщение, у которого `MSH-9.1 = ACK`, не подтверждается: ответ на подтверждение завёл бы петлю ACK↔ACK между двумя автоответчиками, и обмен не кончился бы никогда. В журнал пишется `info` («incoming ACK is not acknowledged»), ответа нет. Тип берётся из `MSH-9.1`, а не из поля целиком: `ACK` и `ACK^R01` — оба подтверждения.

Правило действует и тогда, когда сообщение не разобралось, но `MSH` в нём найден (см. ниже): в журнал пишутся `error` с причиной разбора и `info` о входящем ACK, `AE` не отправляется.

### Неразбираемое сообщение

Неразбираемым считается сообщение, у которого:

- первый сегмент не начинается с `MSH`;
- `MSH` короче четырёх байт (нет `MSH-1`);
- `MSH-1` — не печатный ASCII (например, управляющий байт);
- `MSH-2` содержит не-ASCII байт;
- между разделителями рамки нет ни одного байта.

Во всех этих случаях в журнал пишется событие `error` с причиной. Дальше:

- если `MSH-10` удаётся извлечь — из любого сегмента, начинающегося с `MSH`, с печатным `MSH-1` и ASCII идентификатором — отправляется ACK с `MSA|AE|<MSH-10>`. Первый `MSH` может быть обрезан (короче четырёх байт или с негодным `MSH-1`): тогда ищется следующий `MSH`-сегмент;
- если не удаётся — ответа нет. Подтверждать нечего: без `MSH-10` анализатор не сопоставит ответ со своим сообщением и всё равно повторит передачу.

ACK с `AE` строится на разделителях того `MSH`-сегмента, откуда взят `MSH-10`: оттуда же `MSH-12`, `MSH-3`…`MSH-6` с перестановкой, как у обычного ACK, а `MSH-9` — `ACK`. `MSH-11` копируется из найденного `MSH`, если оно непустое и ASCII; иначе подставляется `P`, как и в обычном ACK при пустом поле. Поэтому `MSA-2` читается по правилам самого сообщения, даже если значение содержит чужой разделитель: в сегменте `MSH#^~\&#…` поле `ID|X^Y` — обычные байты.

Если разделители этого сегмента негодны (в `MSH-2` есть не-ASCII байт), ACK берёт разделители по умолчанию `|^~\&`, а копируемые поля экранируются по HL7: `\F\` вместо `|`, `\S\` вместо `^`, `\R\` вместо `~`, `\E\` вместо `\`, `\T\` вместо `&`. Без экранирования значение развалило бы структуру ACK.

### Закрытие соединения

Когда соединение закрывается, сессия вызывает `finish`: автомат отдаёт то, что осталось в состоянии, и ничего не теряет молча.

- Незакрытая рамка — событие `error` с числом байт, не дождавшихся `0x1C 0x0D`. Пустая рамка (`0x0B` без единого байта данных) ошибкой не считается, как и несколько `0x0B` подряд: терять нечего.
- Хвост мусора вне рамки — событие `info` с числом байт.

`reset` выбрасывает состояние молча и остаётся для COM-порта: там «соединение» — это порт, и закрытия, о котором стоит писать, нет.

### Запросы (FR-18)

Любое сообщение, включая запросы `QRY^Q02`, подтверждается только ACK: `ACK^Q02` и `MSA|AA|<MSH-10>`. Ответных данных (`DSR`, рабочие листы) первая версия не формирует. Запрос целиком попадает в журнал как `data`.

### Примеры

Все примеры синтетические. `<VT>`, `<FS>`, `<CR>` — та же запись управляющих байтов, что в поле `text` журнала (`docs/reference/session-format.md`).

Обычный результат анализатора:

```text
<VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101500||ORU^R01|MSG0001|P|2.3.1<CR>PID|1||PATIENT^TEST|||M<CR><FS><CR>
```

ACK в ответ, время получения `2026-10-19 10:15:30 +03:00`:

```text
<VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101530+0300||ACK^R01|BT261019101530000001|P|2.3.1<CR>MSA|AA|MSG0001<CR><FS><CR>
```

Запрос:

```text
<VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101600||QRY^Q02|MSG0002|P|2.3.1<CR>QRD|20261019101600|R|I|Q1|||1^RD|PATIENT^TEST|RES<CR><FS><CR>
```

```text
<VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101600+0300||ACK^Q02|BT261019101600000001|P|2.3.1<CR>MSA|AA|MSG0002<CR><FS><CR>
```

Нестандартные разделители `MSH-1 = #`, `MSH-2 = $%\*`:

```text
<VT>MSH#$%\*#ANALYZER#LAB#LIS#LAB#20261019101700##ORU$R01#MSG0004#P#2.4<CR>PID#1##PATIENT$TEST<CR><FS><CR>
```

```text
<VT>MSH#$%\*#LIS#LAB#ANALYZER#LAB#20261019101700+0300##ACK$R01#BT261019101700000001#P#2.4<CR>MSA#AA#MSG0004<CR><FS><CR>
```

Неразбираемое сообщение с извлекаемым `MSH-10 = MSG0006`:

```text
<VT>OBX|1|NM|GLU||5.4|mmol/L<CR>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101800||ORU^R01|MSG0006|P|2.3.1<CR><FS><CR>
```

```text
<VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101800+0300||ACK|BT261019101800000001|P|2.3.1<CR>MSA|AE|MSG0006<CR><FS><CR>
```

## ASTM E1381

Профиль `astm_e1381` понимает транспортный уровень E1381 и ничего не знает про записи ASTM E1394: содержимое кадра (`H`, `P`, `O`, `R`, `Q`, `L`) он не разбирает, а подтверждает целиком (FR-17, FR-18).

### Байты обмена

| Байт | Имя | Смысл |
|------|-----|-------|
| `0x05` | `ENQ` | анализатор просит разрешения передавать |
| `0x06` | `ACK` | кадр (или `ENQ`) принят |
| `0x15` | `NAK` | кадр не принят |
| `0x02` | `STX` | начало кадра |
| `0x03` | `ETX` | кадр заканчивает запись |
| `0x17` | `ETB` | кадр заканчивает блок записи, продолжение — следующим кадром |
| `0x04` | `EOT` | передача закончена |
| `0x0D` `0x0A` | `CR` `LF` | конец сегмента, за `CR` — конец кадра |

### Переходы

| Что пришло | Ответ | Состояние после |
|------------|-------|-----------------|
| `ENQ` вне кадра | `ACK` | ждём кадр |
| `STX` | — | собираем кадр |
| `ETX` или `ETB` | — | ждём два знака суммы |
| два знака суммы | `ACK` или `NAK` | ждём `ENQ` или следующий `STX` |
| `EOT` | — | ждём `ENQ`, номер кадра снова 0 |
| мусор вне кадра | — | не меняется |
| недособранный кадр при закрытии | — | `error` в журнал |

Кадр целиком: `STX`, номер кадра `FN` (`0`…`7`), текст записи, `ETX` или `ETB`, два знака контрольной суммы, `CR` `LF`. Поток может быть разрезан на фрагменты как угодно, вплоть до побайтовой передачи: границы кадра, суммы и конца кадра могут попадать на границы фрагментов, а один фрагмент может содержать несколько кадров.

Байт сразу после `STX` — всегда номер кадра, даже если он совпадает с управляющим: номера 2…5 — это те же байты, что `STX`, `ETX`, `EOT` и `ENQ`. Поэтому обрыв кадра управляющим байтом распознаётся только после номера.

### Контрольная сумма

Сумма считается по байтам от `FN` до `ETX`/`ETB` включительно (сам `STX` и всё после терминатора в неё не входят), берётся по модулю 256 и записывается двумя hex-цифрами. На отправку идёт верхний регистр, на приём допускается и нижний: `ab` и `AB` — одна и та же сумма. Знаки, которые не являются hex-цифрами, — негодная рамка: ответ `NAK` независимо от настройки, в журнал `error`.

### Неверная сумма и настройка «NAK на неверную сумму»

По умолчанию кадр с неверной суммой всё равно подтверждается `ACK`, а в журнал пишется `error` «ASTM checksum mismatch: got XX, expected YY». Цель — получить данные: многие приборы считают сумму иначе, а повтор передачи ничего не улучшит (FR-17).

Настройка «NAK на неверную сумму» меняет только ответ: вместо `ACK` уходит `NAK`, `error` в журнал остаётся. Нужна там, где важно заставить анализатор повторить кадр.

`FN` идёт по кругу `0`…`7`. Нарушение последовательности (пропущенный номер, номер вне диапазона) — событие `info`, кадр всё равно подтверждается: данные важнее нумерации. `EOT` обнуляет номер: следующая передача снова начинается с кадра 0.

### Мусор и закрытие соединения

Байты вне кадра ответа не вызывают. Они не теряются: журнал пишет их как обычные `data`, а автомат сообщает о блоке мусора одним `info` с числом байт, когда блок заканчивается, — на `ENQ`, `STX`, `EOT` или при закрытии соединения. `CR` и `LF` вне кадра мусором не считаются: это конец кадра.

`ENQ` и `EOT` посреди кадра обрывают его с событием `info`, `STX` посреди кадра — с событием `error`: новый кадр поверх недособранного означает потерю прежнего.

Кадр длиннее 247 байт от `FN` до `ETX`/`ETB` включительно E1381 не разрешает, но приборы шлют: такой кадр принимается и один раз сообщает о превышении (`info`). Предел, после которого буфер сбрасывается с `error`, — 64 КиБ: иначе поток без терминатора съел бы память (NFR-5).

При закрытии соединения `finish` сообщает о недособранном кадре (`error` с числом байт) и о хвосте мусора (`info`). Пустой кадр (`STX` без единого байта) потерей не считается. `reset` выбрасывает состояние молча — он для COM-порта, где «соединение» не заканчивается само.

### Таймаут

E1381 отводит 15 с на кадр. Автомат сообщает этот срок через `poll_timeout`: от `ENQ` или от последнего байта кадра. Если продолжения нет, недособранный кадр сбрасывается с `error` «incomplete ASTM frame dropped after 15 s», а молчание после `ENQ` — `info` «no ASTM frame within 15 s after ENQ»: кадра ещё не было, терять нечего.

Таймаут нужен и «вместо ЛИС». Без него анализатор, замолчавший посреди кадра, оставлял бы автомат с недособранным кадром до закрытия соединения, а оно может не закрываться часами — и в журнале не было бы ни строки о потере. Если сессия срок не держит, кадр сбрасывается при следующем фрагменте с тем же событием: байты не смешиваются.

### Запросы (FR-18)

Запрос анализатора (запись `Q`) ничем не отличается от результата: `ACK` на кадр, и всё. Ответных кадров (`Q`/`P` с рабочим листом) первая версия не формирует. Запрос целиком попадает в журнал как `data` с `dir: analyzer_to_lis`.

### Примеры

Все примеры синтетические. Байты даны в hex; в поле `text` журнала те же байты выглядят как `<ENQ>`, `<ACK>`, `<STX>`, `<ETX>` и так далее (`docs/reference/session-format.md`).

`ENQ` от анализатора и `ACK` в ответ:

```text
05            →  06
```

Кадр с записью `H|\r` — номер кадра 0, сумма `0x00+0x48+0x7C+0x0D+0x03 = 0xD4`:

```text
02 00 48 7C 0D 03 44 34 0D 0A   →  06
```

Тот же кадр с испорченной суммой по умолчанию тоже получает `ACK`, а в журнал идёт `error` «ASTM checksum mismatch: got D5, expected D4»; с настройкой «NAK на неверную сумму» ответ — `15`.

Длинная запись приходит продолжениями: кадр 0 заканчивается `ETB`, кадр 1 — `ETX`, `FN` растёт, сумма считается у каждого кадра своя.

## Авто (FR-15)

Профиль `auto` — обёртка над готовыми автоматами. Решение принимается один раз на соединение, по первому байту первого непустого фрагмента:

| Первый байт | Профиль |
|-------------|---------|
| `0x0B` (`VT`) | HL7/MLLP |
| `0x05` (`ENQ`) | ASTM E1381 |
| любой другой | «Без ответов» |

Первый байт не теряется: выбранный автомат получает фрагмент целиком, в котором этот байт пришёл. Поэтому разбиение потока на фрагменты не меняет ни ответов, ни событий.

Решение не пересматривается: если на середине обмена придёт байт другого протокола, он достанется выбранному автомату как есть — как мусор или как данные. Для COM-порта «соединение» — это открытие порта: решение принимается на открытие, а `reset` забывает его к следующему.

Нераспознанный протокол не мешает записи: байты идут в журнал как обычные `data`, ответов нет. В журнал пишется `info` с кодом `protocol_undetected`; сообщение английское — «protocol is not detected: the first byte 0xNN is neither 0x0B (HL7/MLLP) nor 0x05 (ASTM E1381); no answers are sent for this connection», — а русскую строку «Протокол не определён — ответы отключены для этого соединения. Запись идёт.» интерфейс берёт по коду.

Пока протокол не определён, байтов автомат не копит: ему достаточно первого байта, поэтому `feed` пустого фрагмента решение не принимает, а `finish` до решения ничего не сообщает.

Настройка «NAK на неверную сумму» (FR-17) доходит и до ASTM-автомата, найденного профилем «Авто»: обёртка передаёт её тому профилю, который выбрала. Без настройки найденный ASTM ведёт себя по умолчанию — подтверждает кадр с неверной суммой и пишет `error` в журнал.
