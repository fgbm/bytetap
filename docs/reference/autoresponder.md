# Автоответчик

Автоответчик отвечает анализатору, чтобы тот не повторял сообщения и продолжал передачу (FR-3). В первой версии он подтверждает обмен на транспортном уровне и не формирует ответов на запросы (FR-18).

Профили (FR-14):

| Профиль | Состояние |
|---------|-----------|
| `hl7_mllp` | HL7/MLLP, описан ниже |
| `none` | «Без ответов»: байты пишутся в журнал, ответов нет |
| `astm_e1381` | появится в M3 |
| `auto` | появится в M3 (определение протокола по первому байту, FR-15) |

Автоответчик не знает ни про сокеты, ни про файл журнала: он получает прочитанные байты и возвращает, что отправить и что записать в журнал. Поэтому его поведение одинаково для TCP и для COM-порта, а проверяется оно без сети.

## HL7/MLLP (FR-16)

### Рамка

Сообщение HL7 передаётся между двумя байтами рамки:

- начало — `0x0B` (`VT`), в записи журнала `<VT>`;
- конец — `0x1C 0x0D` (`FS` `CR`), в записи журнала `<FS><CR>`.

ACK отправляется в такой же рамке: `0x0B` … `0x1C 0x0D`.

Поток может быть разрезан на фрагменты как угодно, вплоть до побайтовой передачи: автомат собирает сообщение из любого числа фрагментов, и `0x1C`, и `0x0D` могут прийти в разных фрагментах.

Правила разбора рамки:

- `0x1C`, за которым идёт не `0x0D`, — обычный байт сообщения; рамка закрывается только парой `0x1C 0x0D`.
- `0x0B` внутри незакрытой рамки означает потерю предыдущего сообщения: в журнал пишется событие `error` («incomplete MLLP frame dropped»), и с этого байта начинается новая рамка.
- Пустая рамка (`0x0B` сразу за ней `0x1C 0x0D`) — неразбираемое сообщение: событие `error`, ответа нет.
- Размер незакрытой рамки ограничен 16 МиБ. При превышении буфер сбрасывается с событием `error`, и до следующего `0x0B` байты считаются мусором вне рамки. Ограничение нужно, чтобы поток без закрывающей пары не съел память (NFR-5).

### Байты вне рамки

Байты вне рамки (`<VT>` ещё не пришёл, или рамка уже закрыта) ответа не вызывают. Они не теряются: журнал получает их как обычные данные (`data`), но в протоколе автоответчика они мусор.

О блоке такого мусора пишется одно событие `info` с числом байтов — когда блок заканчивается, то есть на открывающем `0x0B` следующей рамки. Пока блок не закончился, событие не пишется: длина блока ещё неизвестна. Хвост мусора после последней рамки события не даёт — он заканчивается вместе с соединением.

Пример: `junk` + рамка с `ORU^R01` дают `info` о 4 байтах мусора и один ACK. Мусор в ответ не попадает.

### Разбор сообщения

Сообщение делится на сегменты по `CR` (`0x0D`). Как разделитель сегментов принимаются также `LF` (`0x0A`) и `CR LF`: некоторые приборы шлют так. Пустые сегменты отбрасываются.

Первым сегментом должен быть `MSH`:

- `MSH-1` — четвёртый байт сегмента, печатный ASCII кроме пробела;
- `MSH-2` — разделитель компонентов, повторов, escape и субкомпонентов, столько знаков, сколько есть (в HL7 их четыре, порядок: компонент, повтор, escape, субкомпонент); все байты `MSH-2` — печатный ASCII. Короткий `MSH-2` допустим: чего в нём нет, тем ACK не пользуется. `MSH-2` копируется в ACK байтово как есть.

Событие-триггер берётся из `MSH-9.2` — второго компонента `MSH-9` по компонентному разделителю.

### ACK

| Поле ACK | Значение |
|----------|----------|
| `MSH-1`, `MSH-2` | байтово из входящего `MSH-1`/`MSH-2` |
| `MSH-3`, `MSH-4` | из входящих `MSH-5`, `MSH-6` (перестановка) |
| `MSH-5`, `MSH-6` | из входящих `MSH-3`, `MSH-4` (перестановка) |
| `MSH-7` | время отправки: `YYYYMMDDHHMMSS±ZZZZ`, местное время со смещением от UTC |
| `MSH-8` | пусто |
| `MSH-9` | `ACK` или `ACK<компонент><событие из MSH-9.2>` |
| `MSH-10` | новый идентификатор: `BT`, время отправки и счётчик, только печатный ASCII |
| `MSH-11` | байтово из входящего `MSH-11`; если его нет — `P` |
| `MSH-12` | байтово из входящего `MSH-12`; если его нет — пусто |
| `MSA-1` | `AA` — сообщение принято |
| `MSA-2` | байтово из входящего `MSH-10` |

ACK состоит из двух сегментов, `MSH` и `MSA`, каждый заканчивается `CR`; `CR` заканчивает и весь текст ACK. Поля `MSH` пишутся все до `MSH-12`: пустые остаются на своих местах, поэтому строка MSH может заканчиваться разделителем поля.

`MSH-11` копируется, а не придумывается: если прибор прислал `T`, ACK будет с `T`. Подстановка `P` — только когда входящее поле пустое: пустая процедура обработки выглядит как ошибка формата.

`MSH-10` ACK: `BT` + `YYYYMMDDHHMMSS` + счётчик не короче четырёх цифр, например `BT202610191015300001`. Счётчик сквозной: он не сбрасывается на новое соединение, поэтому в пределах сессии идентификаторы не повторяются.

Время `MSH-7` берётся из того момента, когда автоответчик получил сообщение; часы ему передаёт сессия. Поэтому тесты детерминированы.

### Кодировка ACK — ASCII

ACK всегда ASCII. Копируемое поле переносится байтово только тогда, когда все его байты — печатный ASCII (`0x20`–`0x7E`). Иначе поле остаётся пустым, а в журнал пишется событие `info`: «MSH-3 is not ASCII: the field is left empty in the ACK». Замены на `?` нет: искажённое значение хуже пустого, потому что выглядит достоверным.

То же правило действует для трёх особых случаев:

- `MSH-9.2` не ASCII — тип ACK остаётся `ACK` без события, событие `info`;
- `MSH-10` входящего не ASCII — `MSA-2` пустой, событие `info`;
- компонентного разделителя нет (пустой `MSH-2`) — тип ACK остаётся `ACK`, событие в `MSH-9` не ставится.

### Неразбираемое сообщение

Неразбираемым считается сообщение, у которого:

- первый сегмент не начинается с `MSH`;
- `MSH` короче четырёх байт (нет `MSH-1`);
- `MSH-1` — не печатный ASCII (например, управляющий байт);
- `MSH-2` содержит не-ASCII байт;
- между разделителями рамки нет ни одного байта.

Во всех этих случаях в журнал пишется событие `error` с причиной. Дальше:

- если `MSH-10` удаётся извлечь — из любого сегмента, начинающегося с `MSH`, с печатным `MSH-1` и ASCII идентификатором — отправляется ACK с `MSA|AE|<MSH-10>`;
- если не удаётся — ответа нет. Подтверждать нечего: без `MSH-10` анализатор не сопоставит ответ со своим сообщением и всё равно повторит передачу.

У ACK с `AE` брать разделители неоткуда (сообщение не разобрано), поэтому он строится с разделителями по умолчанию `|^~\&`: `MSH-3`…`MSH-6` пустые, `MSH-9` — `ACK`, `MSH-11` — `P`, `MSH-12` — пусто.

### Запросы (FR-18)

Любое сообщение, включая запросы `QRY^Q02`, подтверждается только ACK: `ACK^Q02` и `MSA|AA|<MSH-10>`. Ответных данных (`DSR`, рабочие листы) первая версия не формирует. Запрос целиком попадает в журнал как `data`.

### Примеры

Все примеры синтетические. `<VT>`, `<FS>`, `<CR>` — та же запись управляющих байтов, что в поле `text` журнала (`docs/reference/session-format.md`).

Обычный результат анализатора:

```text
<VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101500||ORU^R01|MSG0001|P|2.3.1<CR>PID|1||PATIENT^TEST|||M<CR><FS><CR>
```

ACK в ответ, время получения `2026-10-19 10:15:30 +03:00`:

```text
<VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101530+0300||ACK^R01|BT202610191015300001|P|2.3.1<CR>MSA|AA|MSG0001<CR><FS><CR>
```

Запрос:

```text
<VT>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101600||QRY^Q02|MSG0002|P|2.3.1<CR>QRD|20261019101600|R|I|Q1|||1^RD|PATIENT^TEST|RES<CR><FS><CR>
```

```text
<VT>MSH|^~\&|LIS|LAB|ANALYZER|LAB|20261019101600+0300||ACK^Q02|BT202610191016000001|P|2.3.1<CR>MSA|AA|MSG0002<CR><FS><CR>
```

Нестандартные разделители `MSH-1 = #`, `MSH-2 = $%\*`:

```text
<VT>MSH#$%\*#ANALYZER#LAB#LIS#LAB#20261019101700##ORU$R01#MSG0004#P#2.4<CR>PID#1##PATIENT$TEST<CR><FS><CR>
```

```text
<VT>MSH#$%\*#LIS#LAB#ANALYZER#LAB#20261019101700+0300##ACK$R01#BT202610191017000001#P#2.4<CR>MSA#AA#MSG0004<CR><FS><CR>
```

Неразбираемое сообщение с извлекаемым `MSH-10 = MSG0006`:

```text
<VT>OBX|1|NM|GLU||5.4|mmol/L<CR>MSH|^~\&|ANALYZER|LAB|LIS|LAB|20261019101800||ORU^R01|MSG0006|P|2.3.1<CR><FS><CR>
```

```text
<VT>MSH|^~\&|||||20261019101800+0300||ACK|BT202610191018000001|P|<CR>MSA|AE|MSG0006<CR><FS><CR>
```

## ASTM E1381

Появится в M3: `ENQ` → `ACK`, кадр `STX … ETX|ETB cs1 cs2 CR LF` → `ACK`, `EOT` → ожидание, контрольная сумма проверяется (FR-17).
