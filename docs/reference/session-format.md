# Формат журнала сессии

Журнал сессии — один файл в формате JSON Lines: каждая строка — одно событие, целиком в одну строку, UTF-8 без BOM, перевод строки `\n` (FR-24). Поле `format` в заголовке задаёт версию формата; сейчас это `bytetap-session/2`. Формальное описание — JSON Schema [`docs/public/schema/bytetap-session-2.schema.json`](https://github.com/fgbm/bytetap/blob/main/docs/public/schema/bytetap-session-2.schema.json) (draft 2020-12, `oneOf` по полю `type`).

## Версии формата

| Версия | Что нового | Схема |
|--------|------------|-------|
| `bytetap-session/1` | Формат v0.1.0–v0.2.0 | `bytetap-session-1.schema.json` |
| `bytetap-session/2` | Необязательные поля `link` у `open` (вторая сторона пары прокси, FR-5), `repeats` у `info` (число схлопнутых повторов ошибки источника) и `peer` у `error` (адрес отвергнутой входящей стороны, FR-8) | `bytetap-session-2.schema.json` |

Версия `/2` добавлена ровно ради `link`: если дописать необязательное поле в `/1`, старые версии молча считали бы новые журналы битыми (`additionalProperties: false` в схеме), а версия формата об этом не сказала бы. Поля `repeats` у `info` и `peer` у `error` добавлены в `/2` до выпуска v0.3.0, поэтому отдельной версии не потребовало: журналы `/2` без него читаются и проверяются как раньше, а журналов `/2` в выпуске ещё не было. Журналы `/1` читаются и проверяются как раньше: `JournalReader`, `read_all` и просмотр журнала принимают обе версии, а `bytetap-cli verify` выбирает схему по полю `format` и печатает версию. Обратная совместимость односторонняя: новый код читает старые журналы, а `verify` версии v0.2.0 журналы `/2` не проверит — журнал проверяется версией не старше записавшей.

## Файл и папка

- Имя: `bytetap-<YYYYMMDD-HHMMSS>-<режим>.jsonl`, время — начало сессии по местным часам (FR-19). Если такое имя уже занято, к нему добавляется суффикс: `…-tcp_server-2.jsonl`, `…-3.jsonl` и так до `-99`, дальше сессия не стартует.
- Папка по умолчанию: `<домашняя папка>/Documents/bytetap` (crate `dirs`, `home_dir()`), например `C:\Users\user\Documents\bytetap` на Windows; переопределяется параметром.
- «Документы» берутся как папка `Documents` в домашней папке, а не как системная known folder Windows: при Known Folder Move системные «Документы» переносятся в OneDrive, а журналы с данными пациентов не должны синхронизироваться в облако. Если папка журналов всё же оказалась в OneDrive или на сетевом пути (`\\сервер\…`), программа предупреждает об этом при старте.
- Режимы: `tcp_server` (вместо ЛИС по TCP), `tcp_client` (bytetap подключается к анализатору-серверу), `proxy`, `serial` (вместо ЛИС через COM-порт), `com_monitor` (прослушка через два COM-порта), `com_tcp`.
- Имена файлов: `bytetap-20261019-101500-tcp_server.jsonl`, `…-tcp_client.jsonl`, `…-proxy.jsonl`, `…-serial.jsonl`, `…-com_monitor.jsonl` (FR-19, M3-AC16, M4-AC9).

## Порядок строк

1. Первая строка — заголовок `session` (FR-21). Без него файл не считается журналом; заголовок в файле ровно один.
2. Далее события в порядке возникновения: `open`, `data`, `close`, `error`, `info`, `note`.
3. При штатной остановке последняя строка — `session_end` со статистикой.
4. `note` можно дописать после остановки клиентом (`bytetap-cli note`) и во время записи (интерфейс): дописанный после остановки добавляется в конец файла, начало файла не переписывается (FR-23). Поэтому `note` допустим и после `session_end`, а других событий после `session_end` быть не может. Комментарий во время записи стоит между событиями обмена и имеет `mono_us`, как у них.

Фрагменты не склеиваются: разбиение потока на фрагменты — тоже данные, по нему видно, как прибор режет сообщения.

Порядок строк и порядок времени — разные вещи. В прокси каждое направление ведёт свой насос, а `data` пишется в журнал после записи в сокет, поэтому строки двух направлений могут встать не по времени: ответ на круг может оказаться в файле раньше запроса, который его вызвал. Гарантия у формата одна и она о времени: `mono_us` берётся в момент чтения фрагмента из сокета. Отсюда внутри одного направления время не убывает, а между направлениями порядок причинный — время чтения ответа больше времени чтения запроса, на который он отвечает. Кто читает журнал по времени, а не по строкам, получает верную картину; тест `crates/bytetap-core/tests/proxy_order.rs` проверяет это на 10⁴ кругах «запрос — ответ».

## Потеря последней строки

Запись идёт пачками с `flush` и `sync_data` на пачку (FR-20). При аварийном завершении приложения или отключении питания в худшем случае теряется последняя неполная строка: файл может закончиться обрезанной строкой без `\n`. Такой файл считается пригодным: `bytetap-cli verify` сообщает об этом предупреждением и не считает ошибкой. Битая строка в середине файла — ошибка.

Обрезанной считается только последняя строка без `\n`, на которой разбор JSON остановился из-за неожиданного конца ввода, или такая же строка, оборванная посреди многобайтного символа UTF-8. Строка с `\n`, но с синтаксической ошибкой, и строка, где JSON цел, но не является событием формата, — ошибка разбора, а не потеря при обрыве.

Пока идёт сессия, журнал открыт на дописывание, и вторая запись в него запрещена: на Unix это рекомендательная блокировка `flock`, на Windows — режим совместного использования без права записи. Читать файл при этом можно: `bytetap-cli verify`, Блокнот и другие программы видят журнал, пока идёт запись. Дописать комментарий `bytetap-cli note` отказывается: «файл занят: идёт сессия или его держит другая программа». Комментарий в файл с обрезанным хвостом тоже не дописывается — иначе неполная строка слилась бы с комментарием и файл перестал читаться.

Если писатель журнала отказал (ошибка записи на диск, кончилось место), сессия останавливается: последней строкой остаётся последняя записанная, `session_end` не пишется, а `bytetap-cli capture` сообщает «Запись в журнал прервана: …» и выходит с кодом ≠ 0. Подтверждений анализатору после отказа не отправляется, чтобы он не считал обмен успешным, которого нет в журнале. Отказ виден сессии сразу, а не при следующем событии: писатель сообщает о нём отдельно, поэтому замолчавший анализатор не оставляет сессию живой без журнала. В прокси то же место занимает пересылка: после отказа сессия останавливает её и закрывает пару, а не только запись.

Очередь писателя ограничена по объёму — 64 МиБ (`MAX_PENDING_BYTES`). Пока журнал отстаёт, сессия копит события в памяти, но не больше предела: на половине предела в журнал и ленту уходит одно `info` с кодом `journal_backlog_warning`, а на пределе запись отказывает кодом `journal_backlog` — так же, как сломанный диск. Без предела быстрая пересылка при медленном диске съела бы память целиком. Предел считается по оценке длины строки: точная длина вышла бы только сериализацией на пути пересылки, а журнал не должен её тормозить (NFR-6).

Оговорка про ACK: ответ уходит анализатору раньше, чем пачка попадает на диск, — иначе журнал тормозил бы пересылку (NFR-6). Поэтому сообщения, чьи строки были в пачке, писавшейся в момент сбоя, могли получить подтверждение и в журнал не попасть. Отказ обнаруживается по первой неудачной записи; всё, что пришло после неё, уже не подтверждается.

В прокси та же оговорка звучит иначе, и честнее сказать её прямо: кусок, который уже начал уходить в сокет на момент отказа, может дойти до адресата и в журнал не попасть — запись после отказа не принимается. Дальше этого куска байты не идут: сессия останавливает пересылку по первой же неудачной записи.

## Общие поля

| Поле | Тип | Где | Смысл |
|------|-----|-----|-------|
| `type` | строка | везде | Тип события: `session`, `open`, `data`, `close`, `error`, `info`, `note`, `session_end` |
| `t` | строка | все события, кроме `session` | Время по системным часам: RFC 3339 с микросекундами и смещением, например `2026-10-19T10:15:03.000512+03:00` |
| `mono_us` | целое ≥ 0 | `open`, `data`, `close`, `error`, `info`, `session_end`, `note` при живой сессии | Микросекунды от начала сессии по монотонным часам; не зависит от перевода часов |
| `conn` | целое ≥ 1 | `open`, `data`, `close`; необязательно в `error` и `info` | Номер соединения внутри сессии |
| `code` | строка | необязательно в `error` и `info` | Код события для интерфейса: по нему берётся русская строка из i18n, `message` остаётся английским для журнала и поиска (M3-AC16) |
| `repeats` | целое ≥ 1 | необязательно в `info` | Сколько одинаковых ошибок источника схлопнулось в это замечание; есть только у кодов `source_retry_repeats`, `source_recovered` и `source_failing_at_stop`. Поле пишется только при единице и больше: ошибки, сменившиеся без единого повтора, замечания не дают |
| `peer` | строка | необязательно в `error` | Сторона ошибки. У кода `proxy_peer_rejected` — адрес отвергнутой входящей стороны без порта, у ошибок обмена прослушки (`connection_read_failed`, `connection_write_failed`) — имя отказавшего порта (`COM4`). Интерфейс берёт сторону отсюда, а не разбирает английский `message`. У адреса IPv4-mapped запись двойного стека приводится к IPv4: IPv4-клиент слушателя `[::]` виден как `a.b.c.d` |
| `dir` | строка | `data` | `analyzer_to_lis` или `lis_to_analyzer` — всегда относительно анализатора и ЛИС, а не ноутбука |
| `synthetic` | логическое | `data` | `true` — байты сформировал автоответчик, а не прибор и не ЛИС (FR-4) |

`mono_us` и `t` дополняют друг друга: первое даёт точные интервалы внутри сессии, второе — привязку к календарю и часовому поясу.

## События

### `session`

Заголовок сессии, первая строка файла (FR-21).

| Поле | Обязательно | Тип | Смысл |
|------|-------------|-----|-------|
| `format` | да | строка | Версия формата, `bytetap-session/2` |
| `app_version` | да | строка | Версия приложения из `Cargo.toml` |
| `started_at` | да | строка | Начало сессии, RFC 3339 с микросекундами и смещением |
| `mode` | да | строка | Режим работы, см. «Файл и папка» |
| `autoresponder` | да | строка | Профиль автоответчика: `hl7_mllp`, `astm_e1381`, `none`, `auto` |
| `settings` | да | объект | Фактические настройки режима: TCP-сервер — `{"listen": "0.0.0.0:5000"}`; TCP-клиент — `{"connect": "192.168.1.50:5000", "reconnect_sec": 5}`; прокси — `{"listen": "0.0.0.0:50025", "target": "10.0.0.5:5000", "role": "analyzer_client"}`, а с фильтром по адресу входящего — ещё и `"allow_from": "192.168.1.51"` (поля нет, если фильтр не включён: принимать с любого адреса); COM — `{"port": "COM5", "baud": 9600, "format": "8N1", "flow": "none", "dtr": true, "rts": true}`; прослушка двух портов — `{"analyzer": {"port": "COM3", …}, "lis": {"port": "COM4", …}}` с теми же полями в каждом блоке |
| `analyzer` | нет | строка | Модель анализатора, указанная инженером |
| `note` | нет | строка | Комментарий инженера на момент старта |
| `host` | да | объект | `{"os": "..."}` — описание ОС в формате crate `os_info`: тип, версия, издание в скобках, разрядность в квадратных скобках, например `Windows 11 Professional 10.0.22631 [64-bit]` |

```json
{"type":"session","format":"bytetap-session/2","app_version":"0.3.0","started_at":"2026-10-19T10:15:00.123456+03:00","mode":"tcp_server","autoresponder":"hl7_mllp","settings":{"listen":"0.0.0.0:5000"},"analyzer":"ANALYZER","note":"синтетический журнал для тестов","host":{"os":"Windows 11 Professional 10.0.22631 [64-bit]"}}
```

### `open`

Открытие соединения: `t`, `mono_us`, `conn`, `peer` и `local`.

- TCP-сервер: `peer` — адрес и порт анализатора, `local` — локальный адрес сокета, на который пришло соединение.
- TCP-клиент: `peer` — адрес анализатора-сервера, `local` — локальный адрес сокета bytetap. `open` пишется только после успешного подключения.
- Прокси (FR-5): пара соединений — одно соединение журнала с одним `conn`. `peer` — кто пришёл на порт bytetap, `local` — адрес, на котором bytetap слушал. `open` пишется, когда оба сокета уже есть: неудачное подключение к цели пары не создаёт. Поле `link` (только в `/2`) описывает исходящую сторону: `role` — кто на дальнем конце (`analyzer` или `lis`), `peer` — адрес цели, `local` — локальный адрес исходящего сокета. Принятая сторона — противоположная `role`.
- COM-порт: `peer` — имя порта (`COM5`, `/dev/ttyUSB0`), `local` — пустая строка: адресов у порта нет. Каждое открытие порта — новое соединение со следующим `conn` (FR-9, M3-AC2).
- Прослушка двух COM-портов (FR-10, M5-В4): пара открытых портов — одно соединение журнала с одним `conn`. `peer` — имя порта стороны анализатора, `local` — пустая строка, `link` — сторона ЛИС: `role: "lis"`, `peer` — имя её порта, `local` — пустая строка. `open` пишется, когда открыты оба порта: отказ любого из них — ошибка старта до создания журнала. Пропажа адаптера одной стороны закрывает пару, следующее открытие обоих портов даёт новое `open` со следующим `conn`.

```json
{"type":"open","t":"2026-10-22T10:15:00.123456+03:00","mono_us":1000,"conn":1,"peer":"192.168.1.51:49152","local":"192.168.1.10:50025","link":{"role":"lis","peer":"10.0.0.5:5000","local":"192.168.1.10:50231"}}
```

Прослушка двух портов пишет то же поле `link` именами портов:

```json
{"type":"open","t":"2026-10-26T10:15:00.123456+03:00","mono_us":1000,"conn":1,"peer":"COM3","local":"","link":{"role":"lis","peer":"COM4","local":""}}
```

### `data`

Фрагмент обмена (FR-22): `t`, `mono_us`, `conn`, `dir`, `synthetic`, `len`, `b64`, `text`.

- `b64` — исходные байты фрагмента в base64. Это единственный источник правды.
- `len` — длина фрагмента в байтах, равна длине декодированного `b64`.
- `text` — копия для чтения глазами. Кодировки не применяются: байты не-ASCII остаются байтами.
- Ответ автоответчика (`synthetic: true`) записывается после отправки. Если ответ оборвался на середине (таймаут, сброс соединения), в журнале остаётся только фактически отправленная часть — ровно то, что анализатор получил.
- В прокси и в прослушке двух портов `synthetic` всегда `false`: автоответчика в этих режимах нет (FR-6, FR-10). Фрагмент записывается после записи в другой сокет и с фактически переданными байтами, направление — по роли стороны: байты из сокета анализатора `analyzer_to_lis`, из сокета ЛИС `lis_to_analyzer`, независимо от того, кто инициировал соединение.

```json
{"type":"data","t":"2026-10-19T10:15:03.000512+03:00","mono_us":3000389,"conn":1,"dir":"analyzer_to_lis","synthetic":false,"len":20,"b64":"C01TSHxeflwmfEFOQUxZWkVSfEw=","text":"<VT>MSH|^~\\&|ANALYZER|L"}
```

### `close`

Закрытие соединения: `t`, `mono_us`, `conn`, `by`, `reason`.

- `by`: `analyzer`, `lis` или `bytetap` — кто закрыл.
- `reason`: короткий код причины. Используются `eof` (закрытие со стороны собеседника), `reset` (сброс соединения), `stop` (остановка сессии), `error` (закрытие из-за ошибки), `timeout`.
- В прокси `close` пишется один раз на пару (FR-7). `by` — кто закрыл первым: `analyzer`, `lis` или `bytetap`. `FIN` одной стороны пересылается полузакрытием, обратное направление доживает до своего `FIN`, но не дольше 5 секунд; истёк срок — `by: bytetap`, `reason: timeout`. `RST` закрывает обе стороны сразу, «Стоп» — `by: bytetap`, `reason: stop`. Сброс второй стороны во время дожития уходит первой стороне тоже сбросом, но `by` и `reason` остаются за первой: `close` выбирает сторона, закончившаяся первой, а сброс второй лишь передаётся обеим.

### `error`

Ошибка обработки: `t`, `mono_us`, `message`, необязательные `conn` и `code`. Сессия при ошибке продолжается (NFR-5), а соединение не обязательно закрывается: ошибка может быть и такой, после которой обмен идёт дальше, — например неразбираемое сообщение, на которое отправлен `AE`. Закрывает ли ошибка соединение, видно по следующему событию `close` с причиной `error`. У ошибки уровня сессии (не удалось открыть порт, не удалось записать настройку) поля `conn` нет.

Текст `message` у `error` и `info` — английский, независимо от источника (сессия, автоответчик, писатель журнала): журнал читают и человек, и поиск, а CLI-интерфейс остаётся русским. Так, об отказе журнала подписчики получают `error` вида `journal write failed: …; no ACKs are sent after the failure`.

Поле `code` — необязательное, машинно-различимое. Известные коды:

| Код | Где | Смысл |
|-----|-----|-------|
| `accept_failed` | `error` | Не удалось принять соединение TCP-сервера или прокси; повтор с паузой |
| `connect_failed` | `error` | Не удалось подключиться к анализатору-серверу; повтор через интервал |
| `proxy_connect_failed` | `error` | Прокси не подключился к цели (отказ, нет маршрута); входящее закрыто, `open` не писался |
| `proxy_connect_timeout` | `error` | Цель прокси не ответила за срок подключения; входящее закрыто, `open` не писался |
| `proxy_peer_rejected` | `error` | Входящее пришло с адреса, которого нет в `allow_from`: соединение закрыто до подключения к цели, `open` не писался, адрес отвергнутого — отдельным полем `peer` (и в `message` для поиска). Отказы схлопываются в одну серию по коду, а не по тексту: перебор адресов даёт одно событие, а сколько отказов было — в `repeats` замечания о серии. Адрес отвергнутого — без IPv4-mapped префикса: IPv4-клиент слушателя `[::]` виден как `a.b.c.d` |
| `proxy_target_is_self` | `error` | Прокси подключился сам к себе: цель оказалась адресом прослушивания bytetap. Пара не создаётся, входящее закрывается, `open` не пишется; повторы схлопываются в одно событие. Цель, заданная адресом с тем же портом, отвергается на старте; имя узла (`localhost`, имя машины) и порт, который система выбрала вместо `0`, видны только после подключения — их ловит эта ошибка |
| `serial_open_failed` | `error` | Не удалось открыть COM-порт; повтор через интервал. У прослушки двух портов `message` называет порт и его сторону |
| `connection_read_failed` | `error` | Ошибка чтения соединения; соединение закрывается. У прослушки двух портов имя отказавшего порта — в поле `peer` |
| `connection_write_failed` | `error` | Ответ автоответчика не записался целиком, у прослушки — байты не ушли в другой порт; соединение закрывается. У прослушки имя отказавшего порта — в поле `peer` |
| `connection_task_failed` | `error` | Задача насоса пары упала: `close` называет `bytetap` с причиной `error`, пара закрывается. Так отказ ядра виден в журнале, а не выглядит штатным `eof` первой стороны |
| `answer_timeout` | `error` | Ответ не записался за отведённое время; соединение закрыто |
| `journal_failure` | `error` | Писатель журнала отказал; событие только в ленте |
| `journal_backlog` | `error` | Очередь писателя перешла предел (64 МиБ); запись отказала, сессия остановлена. Событие только в ленте |
| `journal_backlog_warning` | `info` | Очередь писателя дошла до половины предела: журнал отстаёт. Одно событие за сессию |
| `source_retry_repeats` | `info` | Ошибка источника сменилась на другую; в `repeats` — сколько раз повторилась прежняя. Перед `error` о новой ошибке |
| `source_recovered` | `info` | Источник снова отдал соединение; в `repeats` — сколько раз повторилась ошибка перед восстановлением |
| `source_failing_at_stop` | `info` | Сессия остановлена, а ошибка источника продолжалась; в `repeats` — сколько раз она повторилась. Последнее `info` перед `session_end` |
| `protocol_undetected` | `info` | «Авто» не распознал протокол по первому байту; ответов нет (FR-15) |
| `timer_resolution` | `info` | Прослушка на Windows подняла разрешение системного таймера до 1 мс на время сессии: без него драйвер отсчитывает таймаут по тику 15,6 мс |
| `control_flow_not_forwarded` | `info` | У порта прослушки включён поток, который сквозь bytetap не идёт: `rtscts` в разрыве не работает, `xonxoff` теряет `0x11` и `0x13`. Одно событие на каждый такой порт, до первого соединения |

Неизвестный код интерфейс показывает общим текстом, а `message` остаётся в журнале.

Опечатка в портах прослушки — не событие журнала, а ошибка старта: если один и тот же порт указан с двух сторон (`COM3` и `\\.\COM3`, `com3`, ссылка и её цель на Unix), пара не открывается, файл журнала не создаётся, а ошибка старта несёт код `monitor_same_port` и имя порта. Своя ошибка, а не «порт занят» от собственного второго открытия: искать чужую программу инженеру не нужно.

### `info`

Замечание обработчика: `t`, `mono_us`, `message`, необязательные `conn`, `code` и `repeats`. Обмен не прерван, но событие стоит внимания инженера: мусор вне рамки MLLP, поле, выброшенное из ACK, входящее подтверждение, которое не подтверждается. Состав полей тот же, что у `error`, плюс `repeats` у замечаний о серии ошибок источника.

Повторы схлопываются: серия одинаковых ошибок источника даёт одно `error`, а сколько их было — видно по `info` с `source_retry_repeats` (серия сменилась), `source_recovered` (источник снова отдал соединение) и `source_failing_at_stop` (серия не закончилась к остановке). Число лежит в отдельном поле `repeats`, а не в английском `message`: интерфейс подставляет его в свою фразу, и разбирать текст журнала ему не нужно. Обычные ошибки считаются серией по тексту, а отказ фильтра адресов `proxy_peer_rejected` — по коду: его текст называет адрес отвергнутого, и по тексту каждый чужой адрес начинал бы новую серию, так что перебор адресов забил бы журнал и ленту. Поэтому сто отказов с двух разных адресов дают одно `error` о первом, а замечание о серии называет в `message` адрес последнего отвергнутого и число повторов в `repeats`.

```json
{"type":"info","t":"2026-10-22T10:16:10.000000+03:00","mono_us":70000000,"code":"source_recovered","repeats":3,"message":"connect recovered after 3 repeated failures: connect failed: connection refused"}
```

```json
{"type":"info","t":"2026-10-19T10:15:03.100000+03:00","mono_us":3100000,"conn":1,"code":"protocol_undetected","message":"protocol is not detected: the first significant byte 0x4D is neither 0x0B (HL7/MLLP) nor 0x05 (ASTM E1381); no answers are sent for this connection"}
```

Замечание без кода (интерфейс покажет `message` из журнала): недописанная запись ASTM после `ETB`-кадра.

```json
{"type":"info","t":"2026-10-19T10:16:44.512000+03:00","mono_us":74112000,"conn":2,"message":"incomplete ASTM record: EOT after an ETB frame"}
```

### `note`

Комментарий инженера: `t`, `text`, необязательный `mono_us`. Может быть первой строкой после `session` (комментарий при старте), стоять между событиями идущей сессии (комментарий, добавленный из интерфейса, — тогда `mono_us` есть) или последней (комментарий, дописанный после остановки, — тогда `mono_us` нет, сессия уже закончилась).

### `session_end`

Итоги сессии при штатной остановке: `t`, `mono_us`, `stats`.

| Поле `stats` | Смысл |
|--------------|-------|
| `connections` | Число соединений за сессию |
| `bytes_analyzer_to_lis` | Байты от анализатора к ЛИС |
| `bytes_lis_to_analyzer` | Байты от ЛИС к анализатору |

```json
{"type":"session_end","t":"2026-10-19T10:15:12.000000+03:00","mono_us":12000000,"stats":{"connections":1,"bytes_analyzer_to_lis":136,"bytes_lis_to_analyzer":76}}
```

## Правила поля `text`

`text` — копия фрагмента для чтения глазами. Правила выбраны так, чтобы `text` однозначно читался обратно в байты: по нему можно восстановить фрагмент, не заглядывая в `b64`.

- Печатные ASCII `0x20`–`0x7E` пишутся как есть, кроме `<`.
- `<` пишется как `<x3C>`. Поэтому любой `<` в `text` всегда начинает экранированную последовательность, а не является частью данных.
- Именованные управляющие символы из FR-22:

| Байт | Запись | Байт | Запись |
|------|--------|------|--------|
| `0x02` | `<STX>` | `0x0A` | `<LF>` |
| `0x03` | `<ETX>` | `0x0B` | `<VT>` |
| `0x04` | `<EOT>` | `0x0D` | `<CR>` |
| `0x05` | `<ENQ>` | `0x15` | `<NAK>` |
| `0x06` | `<ACK>` | `0x17` | `<ETB>` |
| `0x1C` | `<FS>` | | |

- Все остальные байты (`0x00`–`0x01`, `0x07`–`0x09`, `0x0C`, `0x0E`–`0x14`, `0x16`, `0x18`–`0x1B`, `0x1D`–`0x1F`, `0x7F`–`0xFF`) пишутся как `<xHH>`: две шестнадцатеричные цифры в верхнем регистре.
- Запись каноническая: у каждого байта ровно одна форма. `<xHH>` в нижнем регистре, `<x0A>` вместо `<LF>` и `<x20>` вместо самого пробела в `text` не встречаются и считаются ошибкой при обратном разборе. Поэтому `text` целиком описывается шаблоном схемы `^(?:[ -;=-~]|<(?:STX|ETX|EOT|ENQ|ACK|LF|VT|CR|NAK|ETB|FS|x[0-9A-F]{2})>)*$`.

Пример: MLLP-сообщение `0x0B MSH|^~\& … 0x1C 0x0D` читается как `<VT>MSH|^~\&…<FS><CR>`. Кириллица в журнал попадает как `<xD0><x9F>…`, потому что кодировка не угадывается: её выбирает читатель.

## Чтение и проверка

- `bytetap-cli verify <файл>` выбирает схему по полю `format` заголовка (обе версии вшиты в программу), печатает версию формата и проверяет каждую строку по JSON Schema; далее — статистика: число строк, событий по типам (включая `info`), байты по направлениям, соединения. Кроме схемы проверяется то, чего она не видит: `len` равен длине декодированного `b64`, `text` равен экранированию этих байтов, заголовок `session` ровно один и стоит первым, после `session_end` идут только `note`, а суммы байтов не переполняются. Код выхода ≠ 0 при ошибке; обрезанная последняя строка — только предупреждение.
- `bytetap-cli note <файл> <текст>` дописывает событие `note` в конец файла, если журнал не пишется и не оборван.
- Библиотека: `bytetap_core::journal::JournalReader` выдаёт строки с номерами и типизированные события, `bytetap_core::journal::read_all` читает файл целиком.

## Персональные данные

Журнал содержит «сырой» обмен, а значит может содержать ФИО, даты рождения и идентификаторы пациентов (FR-32). Перед публикацией журнала его нужно обезличить вручную; тестовые журналы в репозитории — только синтетические (`ANALYZER`, `LIS`, `PATIENT^TEST`).
